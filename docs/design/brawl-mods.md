# Brawl Mods: whole-game rollback for any build (design)

_2026-10-12. Branch `brawl-mods`. The user's decisions from the conversation of 2026-10-12, plus defaults chosen without asking (marked **default**: say if one is wrong). Nothing here changes the P+ online modes (Direct, Unranked, Ranked, rooms): they keep their in-game menus and gameplay-only rollback._

---

## 1. What it is

A second way to play online, for every build of Brawl that is not the P+ release we ship, and for other GameCube and Wii games where it works:

- **The whole game is rolled back, from boot.** Every player runs the same machine. The menus are shared: everyone sees the same main menu, character select and stage select, and anyone's controller can drive them, as when friends sit at one console. Nothing in the game is ours, so nothing in the game has to be ported per mod.
- **Plug in and out like a controller at a LAN.** A friend who joins gets the running game and their controller is plugged into the next port at an agreed frame. A player who leaves is unplugged the same way. Everyone else keeps playing.
- **The launcher holds the room.** The game shows no room UI. The launcher shows who is in the room, the slots, public or private, kick, and the build everyone must have.

Why: Brawl Minus, REX, vanilla Brawl and other mods have no online play with rollback. Our P+ menus are the best way to play P+, but they cannot follow every mod (tested on Brawl Minus 5.1, 2026-10-12: the plugin loads, the WITH FRIENDS page crashes, and the P+-only state it reads does not exist). Whole-game rollback needs no knowledge of the game.

## 3. How it works, end to end

```
 Launcher (Brawl Mods tab)                Dolphin (one per player)                   mm (rooms, signaling)
 ─────────────────────────                ──────────────────────────                 ─────────────────────
 pick a build, Host ──launch──────────▶   boot the build, solo session  ──hello────▶ room (kind "mods", build hash)
 room window ◀──local control channel──▶  room client, chat overlay      ◀─room-state─
                                          P2P ENet host (session)       ──session ticket (from P2P port)──▶
 friend: Join KFQB ──launch──────────▶    boot nothing yet; join room  ◀─peers' endpoints───
                                          ◀═══════ P2P: machine image, inputs, GekkoNet ═══════▶
                                          plugged in at frame K; play
```

- **Dolphin is the room client**, as it is for P+ rooms today (`Online/Rooms.cpp`, one online connection per account). The launcher talks to the running Dolphin through a **local control channel**: a loopback TCP connection with a random token, both written to `<User>/Online/control.json` (**default**; it replaces file polling for anything live). Room clicks from the launcher's public list reach Dolphin the same way (or through Dolphin's command line when it is not running).
- **Host:** the launcher starts Dolphin with the build and `--mods-room=host[,private]`. Dolphin boots the build, starts a session of one, opens the room on mm and reports it on the control channel; the launcher opens the room window.
- **Join:** the launcher starts Dolphin with `--mods-room=join:KFQB` (or tells the running one). Dolphin joins the room (mm checks the build hash), registers its P2P endpoint, receives the members' endpoints, connects P2P, asks the session host for the machine, loads it, catches up, and is plugged in.
- **Built (2026-10-12), Dolphin's side** (`Online/ModsRoom.cpp`): Dolphin is armed before boot from `PPR_MODS_ROOM` (JSON: `{"host": true, "build": {hash, name}, "public", "controller", "delay", "port"}` or `{"join": "KFQB", ...}`; the command line and the control channel come with the launcher, phase 7). The room's messages go over the Rooms thread's online connection (as chat's do): `mods-create` or `mods-join` once it is up, and again on a new connection (the same code and slot; a new room if it is gone and this player's session still runs). Every `mods-state` becomes the session's members (`Machine::SetRoom`): a new member is a joiner (late); a member who left the room is unplugged when its link drops, or at once when someone else has its slot (GekkoNet drops the old player, the new one is admitted at the next epoch). While mm has no endpoint for this player, the session's own UDP socket sends `mods-endpoint` (with the LAN address, as Slippi's matchmaking finds it); a peer with this player's public address is reached at its LAN one. A peer's `hello` is taken only from one of its addresses, and says whether its sender plays (a joiner learns the session's players from that). Leaving or being removed from the room ends the session there. Harness: `mods_status`, `mods_request` (leave, kick, slot, public).
- **The launcher's hand-off (built)** is two files in Dolphin's online folder, as for P+ rooms (`docs/rooms-protocol.md` §5) rather than a socket: `mods-request.json` in (`{version: 1, id, op: "leave" | "kick" | "slot" | "public" | "controller" | "configure", slot, open, public, controller, createdAt}`; read and deleted within half a second) and `mods-room.json` out (`{version: 1, kind, state: "joining" | "in" | "left", error, room: {code, public, build, host, you, slots: [{slot, open, player: {displayName, connectCode, controller, connected}}]}, session: {phase, error, players, epoch, frame, slot, peers: [{slot, connected, rttMs}]}, input: {controller, index, device, plugged, real}, lastRequest: {id, result, error}, pid, updatedAt}`; on every change and at least every 5 s). Hosting and joining start Dolphin with `--mods-room <json>` (the JSON of `PPR_MODS_ROOM`).

## 4. The build

A build is what the player picks once in the Brawl Mods tab ("Add a build"):

| Part | What | Hash |
|---|---|---|
| Disc | The game's disc image (Brawl: `RSBE01`) | The game ID, revision and Dolphin's disc hash (the same hash the P+ disc check uses) |
| Launcher | Optional `.dol` booted instead of the disc (Minus Launcher, P+ launchers). Riivolution is a later option | SHA-256 of the file |
| SD card | Optional: an image (`sd.raw`) | Only whether there is one: everyone in a room plays the host's card (§6.5) |
| Settings that change what the game computes | Dolphin's emulation settings a session pins anyway (§6.8) | not part of the hash: the session forces them |

- **Build hash** = SHA-256 of the three parts above; shown as 8 hex digits (`3f9a1c07`), full on hover.
- **Known builds** come from a small table in the launcher (`launcher/src/mods/known_builds.ts`): hash → name, version, homepage. The table only names; unknown builds play the same way.
- **The SD card is read-only during a session.** Writes are refused (the game sees a write-protected card) (**default**; Nyx's fork does the same). Saves on the NAND work (§6.5).

## 5. Rooms (server)

Mod rooms live next to P+ rooms in mm (`server/crates/mm/src/mod_rooms.rs`, messages in `server/crates/common/src/mods.rs`), on the same online connection after `hello`, with their own messages rather than a kind on `room-create` (they share nothing with P+ rooms but slots and codes). A player is in at most one room: creating or joining a mod room leaves their P+ room.

| | P+ rooms | Mod rooms |
|---|---|---|
| Create | `room-create {public, ruleset}` | `mods-create {build: {hash, name, disc, discLabel, sd}, public, controller}` (`controller` is `"gc"` or `"wiimote"`; the parts since 2026-10-15, §6.5) |
| Join | anyone | `mods-join {code, build: {hash}, controller}`: only with the same `build.hash` (`mods-error` "You need <name> (<hash>) to join.") |
| Ruleset, rules, stages, sets, ready, teams | yes | **none** |
| Start | when every open slot is ready | **never**: the host's session runs from creation; members plug in |
| Slots | open/close, kick by closing | `mods-slot {slot, open}`, `mods-kick {slot}` (host); `mods-public {public}`; `mods-leave`. Slot moves (`docs` §9 phase 3) later |
| Controller | | `mods-controller {controller}` (any member): what it plays with now, switched mid-game; every member gets the new `mods-state` (nothing when it is the same) |
| State | `room-state` | `mods-state {code, public, build, host, you, token, slots: [{slot, open, player?: {displayName, connectCode, controller, endpoint}}]}` to every member after every change; `mods-left` when the receiver is out (left, kicked, slot closed) |
| Public list | `GET /v1/rooms` | the same response's `modRooms`: code, build, host name, players, open slots (fuller first) |
| Session signaling | room ticket at the start | **`mods-endpoint {token}`**: the member's session sends its `mods-state` token from its P2P UDP port's address on a connection of its own (no `hello`); mm records the address it came from as the member's `endpoint`, answers `mods-endpoint-resp` (with `error` for an unknown token) and closes it. Every member gets the new `mods-state` |

mm stays the only server involved. No game data goes through it: the machine image and inputs are P2P. Room codes are never a live P+ room's code. Rate limits as for P+ rooms. Kicked players cannot rejoin the same room for 10 minutes (**default**). An empty room closes; a host who leaves hands the room to the member who has been in it longest.

## 6. Dolphin

### 6.1 The frame boundary

Snapshots are taken, and inputs change, at a **frame boundary** that must fall on exactly the same instruction on every machine.

- **Brawl builds:** Brawl's main-loop hook (`0x80017504`, `BrawlbackGekkoNetFrameEnd`), as the whole-machine path does today. Checked clean against P+'s and Brawl Minus's codesets (2026-10-12). Every Brawl build runs this `main.dol`.
- **Other games (built 2026-10-13):** the start of each **VI field** (`Machine::OnViBoundary`). The VI's new-field event sets `Machine::g_vi_boundary`, and `CoreTiming::Advance` runs the boundary once its events and the exceptions they raised are done: between two JIT blocks, where a snapshot can be saved and loaded, and where events are serviced at the same instruction on every machine (they already were: every interrupt depends on it). This is the placement of Nyx's fork (Brawlback-Team/Project-Plus-Dolphin, `Dolphin-Wide-Rollback`, "VI New Field", `RunPendingVIBoundary` at the end of `Advance`); no per-instruction guard was needed. The session option `"boundary"` is `"auto"` (default: Brawl's hook for a Brawl build, `IsBrawlGameId`: a disc ID starting `RSB` or a launcher's `ID-...`; the VI field for anything else), `"brawl"` or `"vi"`. When the boundary waits for the players and must give the CPU back (a pause or stop), every CPU core (Jit64, JitArm64, the interpreters) now leaves right after `Advance` instead of running a block, and the next `Advance` takes the same boundary again.
- **What the VI boundary needed besides** (found with New Super Mario Bros. Wii, `SMNE01`):
  - **Brawl's HLE hooks only for Brawl.** They were installed at fixed addresses for every game (`HLE::PatchFixedFunctions`): in any other game they replaced whatever instruction sits there.
  - **The guest's `pc` and `npc` (and the `lwarx` reservation) in a whole-machine snapshot.** Brawl's hook always resumes at its own address, so they were never saved; at a VI boundary the CPU stands anywhere.
  - **A load must not schedule events.** Restoring the video thread's state goes through `AsyncRequests`, whose `QueueEvent` called `Fifo::RunGpu`, which in deterministic dual core schedules the GPU-sync event when syncing is suspended: an event the saved state did not have, and its `ForceExceptionCheck` cut CoreTiming's slice after the load had restored it while the restored downcount stayed, so `slice - downcount` (the cycles run) went negative and time jumped back ~10,500 cycles. Brawl's loop top happens to be a point where this did not show. Now no `RunGpu` from `AsyncRequests` during a whole-machine snapshot's DoState (the video thread is only woken), and a load restores the slice length with the downcount.
  - **The emulated Bluetooth stack's pending requests**: saving rebuilt them from guest RAM (crashed when the RAM there no longer held an ioctlv); saving now writes only their address, and loading refuses a request that is not one (a machine image is hostile data: it read past an empty vector).
  - **The desync checksum counts what changed, not what was written.** A store of the bytes already there marks a granule written on one run of a frame and not on another (same state, other granules marked: thousands at a level load). `RollbackManager` keeps a shadow of RAM as of the newest save (taken with the base snapshot, so a joiner's is its image; updated by every save and every load's restored granules) and the checksum covers only the written granules whose bytes differ from it.
- **Across hosts (NSMB Wii, this PC on Jit64 hosting, the M4 Mac on JitArm64 joining, both on Wii Remotes, LAN):** the first run had a desync every few thousand frames, always the same 13 granules of float arrays holding a NaN: `0x7fc00000` on the PC, `0xffc00000` on the Mac. A NaN an operation generates (no input is a NaN) is negative on arm64 with FPCR.AH set, which Dolphin sets in non-IEEE mode on FEAT_AFP CPUs (§6.6), and positive on PowerPC (Jit64 writes PowerPC's default NaN). JitArm64's accurate-NaN paths left that NaN to the hardware; now the scalar arithmetic path checks its last input too and clears the generated NaN's sign (an integer `BIC` of the top bit of each 16-bit lane: under AH, `FABS` leaves NaNs alone), the paired path does the same for each NaN lane before it puts input NaNs back, and `ps_sum0/1` compute their sum aside and fix it the same way. After: 8 minutes, the last 16,334 frames compared with 0 mismatches; one single-frame desync at frame 9,516 (one granule: four increasing ~4.7M-tick values on the Mac, zeros on the PC, during a load; the machines agreed again at once). Open.
- **Results (2026-10-13, this PC, Jit64, dual core):** NSMB Wii sync test, distance 6 (every frame rolled back 6 and re-run), random Wii Remote + Nunchuk input, 5 minutes: 13,889 frames from boot through the menus into World 1, 19 desyncs, all in the first 637 frames after boot (granules the first run marks written and a re-run does not, bytes the same; a room's host boots alone, so nothing compares those frames: open). A room through a local backend, host and a joiner (machine image, 4 s), both on Wii Remotes: 9,125 frames, 0 mismatches. Brawl Minus on Brawl's hook unchanged (sync test, 7,390 frames, 0 desyncs); Brawl Minus forced onto the VI boundary desynced before the load fixes (not re-run since).

### 6.2 Inputs

Inputs enter where the hardware does, so nothing depends on the game:

- **GameCube pads:** `SI_DeviceGCController::GetPadStatus` already asks netplay (`NetPlay_GetInput`). In a session every SI poll of frame F returns frame F's pad for that port.
- **Wii Remotes:** the emulated Bluetooth stack asks netplay once per Wii Remote update (`BTEmu.cpp`, `NetPlay_GetWiimoteData`, 200 Hz) with a `SerializedWiimoteState` (at most 31 bytes: buttons, acceleration, IR points, MotionPlus, extension). In a session every update of frame F uses frame F's state. Dolphin's netplay sends this state per update in lockstep, which stalls the CPU thread (Nyx disabled Wii Remotes for that reason); we latch it per frame instead, so it is predicted and rolled back like a pad.
- **One player, one port.** A player in slot N drives GameCube port N and Wii Remote N. Their input per frame (**default**, 48 bytes):

  | Bytes | Field |
  |---|---|
  | 0 | flags: bit 0 GC pad present, bit 1 Wii Remote connected |
  | 1-8 | GC pad: buttons (2), stick X/Y, C-stick X/Y, L, R |
  | 9 | Wii Remote state length (0-31) |
  | 10-40 | `SerializedWiimoteState::data` |
  | 41 | a membership request (§6.3): bit 7 admit, bits 0-1 the slot, bit 2 it plays a Wii Remote |
  | 42-47 | reserved, zero |

- **Plugging** is the input itself (built 2026-10-12): every port is a standard controller and every Wii Remote an emulated one on every machine, whoever plays (so a joiner's machine is configured like everyone's). A port whose input lacks the GC flag answers as an empty port; a Wii Remote is connected exactly while its input says so (`WiimoteDevice::Activate`, checked at the start of every frame, the same frame on every machine; none connects at boot). A player who leaves gets GekkoNet's disconnected input (all zero) from the frame the others agreed on, so their controller is unplugged everywhere at once, as at a LAN.
- **Prediction:** a remote player's last confirmed input repeated (GekkoNet's), Wii Remote included.

### 6.3 Sessions and epochs

- **GekkoNet** carries inputs (fixed size, §6.2), as in the P+ paths. Its player count is fixed per session, so a session is a chain of **epochs**: a player joining ends the epoch at an agreed frame K and starts a new GekkoNet session at K with the new set of players. Frame numbers keep counting across epochs (the epoch's frame + GekkoNet's frame).
- **Leaving needs no epoch** (built): GekkoNet's disconnect claims agree on the last frame of the leaver's input, and the others play on with that controller unplugged. A claim carries the leaver's whole input queue (128 inputs of 48 bytes), so the session's limit for a GekkoNet packet is 16 KiB.
- **Agreeing on K** (built): the request travels in the input. The player who admits a joiner (the lowest slot that is playing) sets byte 41 of its input; the first frame F whose input carries it plans the epoch at **K = F + 10** (`EPOCH_LEAD`, more than GekkoNet's prediction window of 7). Nobody can run K before F's input is confirmed, so every machine plans the same K, and a request seen in a mispredicted input is planned again when the frame re-runs. GekkoNet gets a frame limit (`gekko_set_frame_limit`, added to our GekkoNet): it never advances into K but still rolls back earlier frames; when `gekko_confirmed_frame` (added) reaches K-1, every machine holds the same state at K. No proposal, acknowledgement or timeout race.
- **At K:** every player sends the requester a checksum of all its RAM at K (they agree: the players' machines at K are bit-identical, savestates included); the requester sends the joiner the machine image (§6.7), waits for the joiner's checksum of the loaded machine, and tells everyone the new set of players (`epoch_go`). Each starts a new GekkoNet session; the frames its input delay holds back repeat its input of K-1 (`gekko_set_local_delay_input`, added), so no controller unplugs for two frames. If the joiner's image does not load within 120 s, the players go on without it.
- **Input delay (2026-10-15):** each player's own, as in P+: the launcher's setting (`[Online] InputDelay`, which it writes before every launch; `PPR_MODS_ROOM`'s `"delay"` overrides it, 0 is automatic). On automatic it is picked each time a GekkoNet session starts (the session's start and every epoch) with P+'s rule (`Gprb::Session::AutoInputDelay` of `GameRoundTrip`: 1 frame below 90 ms, 2 below 140, 3 below 190, else 4; 100/150/200 until 2026-10-16) from the round trip to the furthest player in it; alone, P+'s default (2). The round trip is the lowest ENet has measured on each connection (`PeerLink::min_rtt_ms`): an epoch starts just after the join's machine image went out, and the inputs that waited behind it are still in ENet's mean. The log says it per GekkoNet session ("input delay 3 (auto, round trip 172 ms)", "input delay 4 (set)"). Until then every room ran at 2 whatever the setting (the launcher never sent `"delay"`): bug #16, a REX room between California and the UK at 167 ms, stuttered on the UK side's Ryzen 5 2600 (the longest frame of every 10 s 45-77 ms, some 310-390 ms; 30 ms alone) while the same pair's P+ games at delay 4 ran at 59.9 frames/s. Checked with `harness/tools/machine_join.py --delay` (REX TE 1.1.1, a late join through netsim at 167 ms): on auto, with a 16 Mbit/s uplink and a 100 ms buffer, the host started at 2 (alone) and both picked 3 at the epoch (round trips 172 and 170 ms), 0 desyncs; set to 4, both kept 4 across the join, 0 desyncs. `machine_pace.py` takes `--delay` too; an A/B of 2 against 4 at 167 ms did not get a game going (one run held at frame 2439 in an OS wait on both machines, the other never started its session), so the effect on REX's rollbacks is not measured here.
- **Transport:** the P2P ENet hosts and hole punching of `Online/Matchmaking.cpp`, with GekkoNet's adapter over them (as `GameplaySession` does). Channel 0: GekkoNet; channel 1: session control (JSON, small); channel 2: machine images (§6.7), rate-limited.
- **Pacing, time sync, presentation:** reused from the P+ gameplay session where they are not Brawl-specific (`CoreTimingManager::BeginRollbackBurst`, present pacing, audio clock waiting during resimulated passes). The rollback burst was not actually begun until 2026-10-14: the throttle re-anchored at the presented frame after every re-run, so each rollback's re-run time was lost for good, and REX rooms ran at 57 frames/s in prod at 50 ms. Measured on this PC (two Dolphins, REX, netsim 50 ms, random input; `PPR_MACHINE_OLD_THROTTLE=1` for the old behaviour): 4-6 rollbacks/s, 54.7 frames/s before (median second 56.9), 58.2 after (median 59.9, as with no input at all, 59.85); 1.4 rollbacks/s, 57.9 before (median 59.2), 58.7 after (59.9). A plain Dolphin, a session alone and two at rest run 59.9. What is left of the mean is REX's own scene loads (the same in a plain Dolphin, among them a 0.75 s stop with no video fields at one scene change). Present pacing was not on either until 2026-10-16 (bug #30, a REX room between New York and the UK, "a bit of choppiness": 83 ms, no loss, 59.9 frames/s): only `GameplaySession` called `SetPresentPacing`, so a room showed each frame as soon as the CPU reached its copy, 16 ms apart with a 21 ms gap every seventh frame. The session now turns it on when it starts running and off when it stops, fails or the game runs on alone. Two Dolphins, REX TE 1.1.1, netsim 83 ms, delay 2, D3D11, seeded input, 2 minutes of play (`RollbackPresentPacing=False` for before), before / after: presents off a field by over 2.5 ms 22.7 / 5.3 %, over 20 ms apart 9.5 / 1.9 %, over 25 ms 1.9 / 0.18 %, 59.15 / 59.6 frames/s, 0 desyncs. `PPR_MACHINE_PACE_LOG=1` logs a line a second of where a session's time goes (displayed and re-run frames, rollbacks, waits for GekkoNet, late frames, time-sync speed, frames ahead, the throttle's lag).

### 6.4 Snapshots

`RollbackManager` in whole-machine mode (not region mode): MEM1, MEM2, the locked L1 cache and Dolphin's device state, saved incrementally (64-byte granules written since the last save). Measured on P+ (2026-10, Fox/Falco, distance 2): **0.90 ms per save, 1.57 ms per load**. The Brawl-specific parts of the path that exists today move behind the session: pads written into Brawl's `gfPadStatus` (replaced by §6.2), Brawl's desync checksums (replaced by §6.6), the Brawl frame counter.

**What a rollback costs, and the JIT (2026-10-14).** After the throttle fix (§6.3) a REX room in prod ran at 59.7 frames/s but stuttered all game. `PPR_MACHINE_PACE_LOG=1` now also logs, per second, each load's parts (its wait for the video thread, the device states, the granules restored and how many of them it changed, the JIT step and whether it dropped blocks), each re-run frame (from its pass's start to the next pass's: the frame and its save) and each save, and a frame profile of re-run and shown frames (`Rollback::FrameProfile`, now in machine sessions too: JIT compile time and blocks, CoreTiming events by kind, waits for the GPU thread, the GPU thread's busy time, the throttle); `harness/tools/machine_pace.py` runs a setup (a session alone, with or without a sync test, or two through netsim) and sums these up per machine. Two Dolphins on this PC, REX TE 1.1.1, netsim at 50 ms, fast random input, Null video: a re-run frame took **14.3-14.7 ms, 10.1-10.5 ms of it compiling ~500 JIT blocks**, against ~2-3 ms for a first run; a load took 3.0 ms. Every load dropped the JIT's blocks of every restored granule (§6.6), about 55,000 granules a rollback, and REX's codes keep their data next to their code, so each rollback threw away hundreds of hot blocks that the re-run compiled again. About 93% of those granules held the same bytes again after the restore.

Now a load keeps the JIT's blocks unless code went away since its snapshot: the block cache counts what it loses (a block destroyed, the cache cleared, a line invalidated, a per-instruction hint learned or dropped; `JitBaseBlockCache::Invalidations`), each snapshot keeps the count, and a load whose count differs, or whose restore changes an instruction a block was compiled from (`HasCodeAt` on the changed words), drops the restored granules' blocks as before (`RollbackManager::JitKeepsBlocks`). Otherwise the cache only gained blocks since, of code that was there at the snapshot's frame. It is one or the other, never some of the blocks: compiling reads the code through the emulated instruction cache (machine state), and a block recompiled with a hint learned since (a gather pipe write's interrupt check) takes interrupts elsewhere. Restored granules whose bytes did not change are no longer copied. `PPR_MACHINE_JIT_ERASE_ALL=1` drops every time, as before (A/B); `PPR_MACHINE_NO_JIT_ERASE` never does (bisection). Results, same setup: **a re-run frame 3.4 ms (was 14.3-14.7), a load 1.2 ms (was 3.0)**, the JIT compiling nothing in re-run frames. Sync test at distance 7 (every frame rolled back 6 and re-run): idle at the title screen 59.9 frames/s (46.5 with the old drop); about 1-3% of loads drop blocks (scene changes).

`PPR_MACHINE_TEST_INPUT=SEED[:FIRST]` plays the local GameCube pad from a seed as a function of the frame alone (from frame 900 by default), so two builds take the same path whatever their speed; random input sent by the harness in real time did not (the faster build got further). With it, the sync test at distance 7, seed 11: 5,977 frames, 0 desyncs (old drop: 4,667 frames, 0 desyncs); seed 12: both stop for good at frame 3755, where a match ends and the menu loads (the guest in an OS wait loop, not crashed), the same state with the old drop and the new rule; without rollbacks the same seed plays on past frame 9,000. Open. Found on the way: REX TE crashes (its OS's fatal handler, r1 = 0xfffffc29) in the Vault's movie menu when it plays a movie it does not ship (`2006_E3.thp`, "SDStreamOpen Failed"), the same with and without rollbacks; seed 3 reaches it. And harness test sessions (`PPR_MACHINE_SESSION`, no room, no build store) lost the save their NAND started with since 5b60bbe0, so Brawl's boot message about it could hold them; a session without a store keeps it again (rooms unchanged).

### 6.5 NAND and SD

- **NAND:** the session runs on a temporary NAND, as Dolphin's netplay does. A rollback must also undo file writes: a **write journal** records each file's previous contents (or absence) at its first change after a snapshot; a load undoes the journal back to the snapshot's mark (**default**; Orca and Nyx do this, `IOS/FS/HostBackend/Journal.cpp`, GPL, ported with attribution). Saves made during the session are written back to the player's own NAND at the end only if the user ticks "Keep saves from this session" (**default** off).
- **Saves, per build (built 2026-10-14, the user's choice):** each build (game hash) has its own save store, `<User>/Saves/<first 16 hex digits of the build hash>/`, laid out like a NAND root. A session's NAND starts from the store's save of the game, or with none (the game makes its own) when the store has none yet: the session's NAND is seeded with P+'s template save, whose files of that title are deleted. Until 2026-10-14 a Brawl-based build with no save started from P+'s save and kept it, P+'s name tags and controls ("NoTap") included (prod: REX, vanilla Brawl); the launcher deletes each build store that holds a Brawl save once (`launcher/src/dolphin/mods/template_saves.ts`, marker `Saves/.pplus-template-saves-cleared`). At the end the session's save goes back to the store when this player booted the game (the room's host at its start); a joiner plays the host's save, which comes with the host's machine image, and its store is never written. P+'s NAND (the netplay User folder's `Wii/`) is neither read nor written by sessions: every Brawl mod uses Brawl's title (RSBE01), so per title P+ and every mod would share one save; per build each has its own. The copy is the title's whole NAND folder with its metadata (`CopyNandTree`), not `WiiSave::Copy`, which rebuilds a save from its parts and can leave files behind. Before 2026-10-14 the session's NAND was copied back over the player's own at the end (it is not Dolphin's netplay, so nothing stopped Dolphin's cleanup), which broke P+'s Brawl save on staging ("Create a save file?").
  - **Importing a save (built 2026-10-19, the user's choice; bug report #55).** A room never reads Dolphin's own NAND, so TIRE#6's NSMB Wii save, imported into Dolphin, never reached their room: it played the fresh save their first room had made. A Wii game's edit window (the pencil) has **Import save** (from a `data.bin`, as Dolphin's Export Wii Save or a Wii writes it, or from a folder: a Dolphin User folder, its `Wii` folder, or the save's own `title/<hi>/<lo>[/data]` folder) and **Open save location** (the store's `title/<hi>/<lo>/data`, made if missing), with the save's file count and last change. The launcher does it (`launcher/src/dolphin/mods/save_import.ts`): the `data.bin` reader is Dolphin's `WiiSave` DataBinStorage ported (the SD key, the header's MD5, each file's AES-CBC), file names are escaped as `Common::EscapeFileName` does, and the files are plain host files, which the store's HostFileSystem gives owner 0, group 0 and read-write for everyone, as every file a session wrote back already has. The title ID comes from the disc's header (`ModBuild.titleId`; MKW's is `00010004...`). Another game's save is refused; the new save is written in full before the old one moves to `<User>/SaveBackups/<16 hex>/<time>/data` (the newest 10 kept); nothing is imported while a room runs, since the session writes its save back at the end. GameCube games have no section (memory cards are not kept).
- **SD card, synced before the join (the user's decisions, 2026-10-15; built 2026-10-15, it replaces the fetching while the game runs of the next item).** Bug reports #2 and #4 (prod, 2026-10-14, REX, SARA#694 hosting, BUDS#979 joining): the joiner's card was another REX release (4485 chunks, 280 MB, differed; the host's newest file is dated 2026-06-08 and REX's files changed in May and June add up to 243 MB), and every first read of a differing chunk waited a round trip, 65-490 ms each and about 50 in a row at one load: the joiner froze, and the host with it once its rollback window ran out. A fetch while the game runs is a freeze by construction (the read must give every machine the same bytes at the same emulated time), however well it prefetches, so **a session never reads a byte the player has not got**:
  - **Before the join:** in the room, the joiner gets the host's manifest and a file list (path, size, chunks), compares them with its own card's cached hashes and, if anything differs, shows a dialog before anything else: "Your SD card is 280 MB different from the host's (412 files). Download it? ETA: 4 minutes"; under it, in yellow, "(!) SD cards can be used to run code on your Wii. Only download from a friend you trust, never a stranger."; then **[No] [Yes] [Yes, and overwrite local card]**. No leaves the room. The download runs while the room plays on; the joiner asks to be admitted (the epoch, where the room waits for the machine image) only once it has every chunk. Yes keeps the fetched chunks beside the player's card, which stays as it was; the third writes them into it.
  - **While the game runs:** no SD traffic at all, no background stream (bug report #4's 277 MB stream ran the whole session). A read of a chunk the joiner has not got is a bug (logged, failed in tests), never a wait.
  - **The host hashes its card once** (the hash cache, by size and modification time; sessions never write the card).
  - **Rooms show each part's hash** instead of one build hash (the launcher already hashes the parts, `build_hash.ts`): "Brawl: abcdef", "SD card: abcxyz". A different disc is a red X and greys the room out (a disc cannot be sent); its tooltip: "Brawl ISOs don't match. Make sure you're both on the same revision." (with each player's revision). A different card is amber and the room stays joinable through the dialog; its tooltip: "SD cards do not match." Clicking a hash opens the game's edit window with that field pulsing gold until it is clicked. The launcher `.elf` goes with the card (small, the mod's own code like the card's codes). The card's hash is the canonical manifest's, so free space (deleted data) never makes two cards differ.
  - **Writes and retail games:** the card stays write-protected in a session. A retail game gets no card: Wii games keep their saves on the NAND and use the SD card only for media, DLC and custom music; REX also keeps its name tags and controls in its NAND save (`autosv0.bin`).
  - **Security:** joining already runs the host's code (the machine image, §7); the card adds persistence, since "overwrite local card" writes a host's bytes into a card the player may boot outside our sandbox. The yellow warning is the guard (the user: a disclaimer is enough). Chunks can come from any player, so the chunk hash becomes a cryptographic one (BLAKE3) instead of XXH3-128.

The join's timeout counts from then. At the machine image the joiner plays that card (its manifest must be the image's); no background stream, and a read of a chunk it still has not got is logged as an error ("the game read N chunks this player had not got ... a bug") and fetched. The card's file list comes from its FAT (`ListCardFiles`: FAT16/FAT32, long names, chains bounded) and is checked like everything a player sends (`ReadFileList`: counts, paths, runs within the card). DolphinTool's `sdhash -i <card> -u <User> [-p]` prints a card's root (and caches its hashes in that User folder, the netplay Dolphin's, so a room's session never reads the card again).
  - **The upload is paced (the user, 2026-10-15: a 250 MB difference must not lag the game being played; built 2026-10-15).** Every player that has the card sends a share (`RequestChunksLocked`: each chunk to the player with the least asked of it for what it sends; a retry to another one), and each paces its own upload (`PaceSD`), as BitTorrent's uTP and OS updates do (LEDBAT, RFC 6817): a token bucket whose rate grows while the joiner's link shows no queue and shrinks as soon as it does (its round trip's lowest of the last 500 ms over the connection's lowest; that link crosses the sender's own uplink one way, the joiner sends back only acknowledgements), aiming at 6 ms of queue (ENet's timing shows 3-4 ms with none); a game link to another player queueing past 18 ms halves it at once. It climbs fast only to 85 % of the rate a queue last showed at, then probes 0.2 % a step, so it holds a little under what the uplink can take instead of overshooting into a queue every few seconds. Chunks go out in 4 KiB slices (`SD_PIECE`), so a game packet waits behind at most one slice (a whole 64 KiB chunk is 64 ms at 8 Mbit/s); every session link pings every 50 ms so a game link's round trip is fresh. A link's queue is the lowest round trip of its last 100 ms over the connection's lowest (`SteadyQueueMs`; 500 ms showed a queue just begun half a second late, and the rate went a fifth past the uplink meanwhile once the congestion window no longer halved on its own needless resends, §6.7); on a jittery link (its round trip changing by over 8 ms from one send 30 ms or more after another, beyond a trend: 2-4 ms on a clean link, 8-14 with normal jitter of 10 ms, 30-45 with pareto 25) it is the lowest of the last 3 s of half-second readings, since jitter alone kept the half second's lowest 3-73 ms over the connection's lowest with nothing queued (pareto) and the upload sat at its least, 32 KB/s. The rate grows only while the rate holds the upload back, not ENet's window. ### 6.6 Desyncs

- Each confirmed frame's checksum (GekkoNet compares them) is **CRC32 of the granules of MEM1 and MEM2 written in the frame whose bytes changed, plus a rotating 1/360 slice of all RAM** (every byte is covered every 6 s). EFB and XFB copies stay on the GPU in a session (pinned), so nothing rendered reaches guest RAM: with copies to RAM, a dual-core re-run diverged where Brawl reads rendered pixels back (`docs/determinism-findings.md`). Since 2026-10-15 a copy writes nothing at all into guest RAM in a session (below), so no granule is skipped as GPU-written any more (the skip, `GPUWrittenBitmap`, kept a mark made by a pass a rollback undid, so a copy only one machine predicted left its bytes skipped on that machine alone).
- **A desync is the machines' memory differing, and the players are told** (built 2026-10-15): the first desync of a burst puts "Desync with <player> at frame N: your games differ." in the chat window (at most every 30 s) besides the log line. Planned, not built: the session host sends its machine to the players that differ (§6.7) and twice in a minute ends the session (**default**); until then a joiner that leaves and joins again gets the host's machine.
- **What desynced in bug 16** (2026-10-15; a REX TE 1.1.1 room, California to the UK at ~167 ms, host on a Ryzen 5 2600: 2-3 frame bursts at a join's epoch and mid-match, none lasting). Not false checksums: the two machines' emulated time parted, and with it everything the game stores from the time base (OS ticks on stacks, timers). Three causes, each found by `harness/tools/machine_desync.py --match` (a host at REX's character select, a joiner joining there through netsim at 167 ms, delay 2, both picking and playing a match with harness fighters) and the I/O log's block probe (`PPR_MACHINE_IOLOG=-12`, `PPR_MACHINE_IOLOG_BLOCKS=1`, which now logs each block's time), each the first difference after the one before was fixed:
  1. **Copies kept in VRAM still wrote guest RAM from the video thread.** Dolphin fills a pinned copy's destination (zeros, fuchsia for an XFB) and a backend without VRAM copies (Null) writes the copy itself, both whenever the video thread gets to it; REX's character select reads that memory, and one frame later the joiner reached its loop top 350 cycles before the host (three 600 KB XFB writes a frame, at other instructions on the two machines). On the player's D3D11 these were the fills, and an overloaded host's video thread runs seconds behind (the epoch's 6.6 s stall had 5.9 s of video-thread CPU). Now `PresentStats::SetCopiesLeaveGuestRAM` (from `Machine::Arm` to `Stop`) keeps every copy out of guest RAM: no fill, no write, no GPU-written mark.
  2. **The JIT's `dcbx` loop.** Jit64 and JitArm64 run a `dcbst`/`addi`/`bdnz` cache loop as one native loop for as many lines as the downcount allows, but inside a block the downcount is behind by the cycles the block ran before it, and whether the loop is fused at all depends on where the block began, i.e. on the machine's JIT history (a joiner compiles from its join on; a rollback keeps or drops blocks). At REX's character select a decrementer interrupt was taken 4 cycles late on the host and 25 on the joiner. Not fused where `Core::WantsDeterminism` (a session, a movie, netplay).
  3. **The loop-top hook's yield cost emulated time.** When the boundary has to give the CPU back while it waits for the players (`cpu.GetState() != Running`: another thread's `CPUThreadGuard`, which the harness's memory reads and some of Dolphin's own jobs take), the Brawl hook went on to the loop end and back, a few hundred cycles each pass, so that machine's frame came later. Now the hook asks to be run again (`Machine::TakeHookYield`) and Jit64, JitArm64 and both interpreters leave for the CPU loop right after it, counting only the block's instructions before the hook, and come back at the same emulated time (the VI-field boundary already did this in `Advance`).
  Before (same flow, 9 runs): every run desynced, 27-570 frames after the join, then on hundreds to thousands of frames. After all three: 0 desyncs (block probe on: 3,700 frames from the join through a match and its results; full speed, 10 minutes: 35,900 frames from the join through a match, 467 and 427 rollbacks). Not built here: JitArm64 (written to match Jit64, not compiled on this PC). The diagnostics: `PPR_MACHINE_DIGESTS=1` keeps, per frame, the granules the checksum found changed (with whether each was counted) and the slice's CRC alone, and `machine_digest` returns them, so the tool tells memory that differs from memory counted differently; `=2` keeps their bytes (`--bytes N`); the first rollbacks of each epoch are logged.
- **What a rollback restores** (found with the sync test's diagnostics, 2026-10-12): a whole-machine snapshot carries, besides RAM and every device's state, the MSR and every SPR (the gameplay-only snapshots keep the 18 a game changes) and the instruction cache. The MSR's FP bit is the OS's lazy FPU switch: a re-run that took the FP-unavailable exception where the first run did not (its MSR was the thrown-away timeline's) ran the handler's cycles more, Brawl's main loop then counted two retraces instead of one, and the machines diverged. The JIT compiles through the instruction cache: after a scene change the thrown-away timeline had left a new module's code in lines where the restored memory holds the old one. About half of the 5-minute sync tests at distance 7 desynced before; 0 of 11 after (single and dual core).
- **What a rollback loads** (bug 25, 2026-10-16: in a REX room no third player could join, "player 2 does not vouch for this machine", and the two players desynced from then on). GekkoNet's load names the frame whose end state to restore, and the ring's newest slot holds the end of the last frame run (`s.current_frame`). The session counted it from the update's last advance instead (as `NetPlayClient` does), which is one frame short whenever GekkoNet re-runs frames without a new one: while it waits for a player's input, and always while every machine holds before an epoch's frame. That machine then ran a frame ahead of its frame numbers: per-frame checksums mismatched from there on, and at an epoch its full checksum was another frame's. A 2-player room never showed it at a join (its host is alone at the epoch, with nothing to roll back), a third player always could. GameplaySession had the same bug fixed on 2026-10-10. Now every first pass after a load checks that it starts at the emulated time the frame's last run started at, and logs "rollback N frame(s) back (ring R): frame F starts at T ticks, its last run at T' (+D)" if not. `harness/tools/machine_join3.py` (host, a joiner, then a second joiner; REX 0½ Hotfix 1, 90 ms): before, 4 of 4 runs desynced (one refused the third player at its epoch, three desynced 13-500 frames after it); after, 4 of 4 with the third player in and 0 desyncs over 4,600-6,700 frames each (760-1,340 rollbacks a machine, no load of the wrong frame).
- **Code caches at an epoch**: every player empties its instruction cache and drops its JIT blocks for RAM at the epoch's frame, the state a joiner starts in (a joiner's machine image carries neither).
- **The time base** a session's guest reads is the instruction's own, not its JIT block's start (Jit64 and JitArm64 `mftb`; upstream leaves it at the block's start for a game that breaks otherwise).
- **Across hosts (Windows x86-64 and an M4 Mac, 2026-10-13)**: a Mac joiner differed from the PC in ~800 granules from the epoch's first frame, the same with JIT or cached interpreter on the PC, any video backend. With the host's I/O log the two machines' inputs (MMIO reads, host writes) were the same up to one CPU store, and the instruction trace showed `ps_abs` leaving a negative value negative on the Mac. Brawl runs in non-IEEE mode (FPSCR.NI), for which Dolphin sets FPCR.AH (with FZ) on hosts with FEAT_AFP so that only outputs flush, as on x86; under AH, FABS and FNEG leave a NaN unchanged, and clang builds the mask 0x7FF...F as FNEG of all ones (a NaN): `Interpreter::ps_abs`, `std::copysign` in `fctiw`'s rounding and in `fres` (`Common::ApproximateReciprocal`) kept the sign, and the DVD's timing math had the same mask. Fixed: sign changes in the interpreter go through `Common::ClearSignBit`/`SetSignBit`/`FlipSignBit`/`CopySign` (integer ops on a mask the compiler cannot see through, `Common/FloatUtils.h`); the DVD's read scheduling runs in the host's default FPU mode (`Common::FPU::ScopedDefaultSIMDState`); and the build passes `-ffp-contract=off` to clang and gcc, as MSVC's `/fp:precise` already does (clang fuses `a * b + c` on arm64). A session on arm64 runs the cached interpreter (JitArm64 marks no dirty pages), so the interpreter's C++ is what has to agree with x86. After the fix the first frames after a Mac's join are the same granule for granule.
- **No host network in a session**: the next cross-host desync came ~2 minutes in, where the test's random inputs had reached Brawl's Wi-Fi menu: Nintendo Wi-Fi Connection's login asked for `naswii.nintendowifi.net` through `IOCTLV_SO_GETADDRINFO`, which Dolphin answers from the host's DNS on a worker thread, writing the answer into guest memory when the host has it (a frame later on the Mac, with other contents). The IP stack's vector ioctls now refuse like its plain ones under `Core::WantsDeterminism` (a session sets it), and so do WiiConnect24's network requests and its wall-clock scheduler. A session's guest has no network at all (also `docs/brawl-mods-security.md` §3).
- **One CPU core for everyone** (measured 2026-10-13): with both fixes a PC and a Mac on the cached interpreter stayed in sync for 16,180 frames; a PC on Jit64 against the Mac differed in ~35 granules from the first frame (saved FPRs in the OS thread contexts, and timebase values a few ticks apart: the JIT and the interpreter count cycles differently). Every machine in a session has to run the same core. But the cached interpreter runs Brawl at **35 frames/s** unthrottled on a Ryzen 7 9800X3D (Jit64: 600), below full speed before any rollback: a session on the cached interpreter is not playable. **Cross-play on the JITs (built 2026-10-13):** a session on arm64 runs JitArm64 (its fast stores mark dirty pages since a3fd38ff; a sync test on the M4 at distance 7: 5,864 frames, 0 desyncs) and pins FPRF, accurate NaNs and FMA on, so the two JITs and their interpreter fallbacks compute alike. Jit64 and JitArm64 then count the same cycles; what still differed, found with the I/O log's CoreTiming events and a probe at every block's entry (`PPR_MACHINE_IOLOG_BLOCKS`, with `PPR_MACHINE_IOLOG_BLOCK_DUMP` for the FPRs at chosen blocks): (1) the upper word of fctiwz's result, 0xFFFF0000 on the Mac: the arm64 emitter encoded 16-bit-lane ORR/BIC immediates as 32-bit lanes (upstream); (2) Jit64's mftb took the 32-bit conversion of a negative downcount as 64 bits (a time base 0x15555555 ahead); (3) ps1 after a double-precision result: the interpreter and JitArm64 keep the destination's ps1, Jit64 gave it the first source's with AVX three-operand ops (VMULSD d, a, b copies a's upper half: Jit64 differed between hosts with and without AVX), after a MOVSD from memory (zeroes it) and after write-only binds (whatever the host register held) in fneg/fabs/fnabs, fctiw and frsqrte. It shows only where the OS saves a thread's paired singles (psq_st of both halves into its OSContext), which every thread switch does. Fixed in Jit64. Result: a PC on Jit64 and an M4 Mac on JitArm64 stayed in sync for 10,751 frames, 0 mismatches. Seen on the way, not fixed: with some floating-point JIT categories turned off (`Debug.JitFloatingPointOff` and the like, a debugging setting) JitArm64 corrupted the heap during boot; with all of them on (the default) it never did.
- **Diagnostics across hosts**: `PPR_MACHINE_IOLOG=N` (with `PPR_MACHINE_DUMP_DIR`) writes the first N frames after the epoch: every MMIO read, every host write into guest RAM (and, with an interpreter core, every CPU store) with CRCs of the FPRs and GPRs; `-K` keeps the last K frames and writes them at the first desync; `PPR_MACHINE_IOLOG_REGS=FRAME:FIRST-LAST` adds the registers, the code around pc and each instruction the cached interpreter ran, for those events. Two machines' logs give the first instruction whose result differs.
- **Diagnostics** (sync test, `PPR_MACHINE_SESSION={"synctest":N}`): each re-run of a frame is compared with its first run: the granules that differ (`diag` in `machine_status`); `PPR_MACHINE_EVENT_TRACE=1` adds the CoreTiming events each pass ran with the guest CPU's pc, lr, r1 and registers at each (the first event where they differ); `PPR_MACHINE_STATE_CHECK=N` compares the whole state as an image carries it, and the NAND, at the start of every Nth frame's passes (`PPR_MACHINE_DUMP_DIR` keeps the first pair that differs); `PPR_MACHINE_NO_JIT_ERASE` and `PPR_MACHINE_JIT_CLEAR_EACH_PASS` change what a rollback does to the JIT (bisection only).

### 6.7 Joining: the machine image

**Built (2026-10-12), version 1: the players wait at K while the image travels.**

1. The joiner's Dolphin boots the same build, runs its first scBoot frame on its own and waits at the next loop top. That loop top starts a JIT block of its own, as the players' loop tops do, so the image loads at the same instruction (loaded in the middle of a longer block, the block's remaining cycles would be counted after the load).
2. The requester captures the image at K's loop top: Dolphin's savestate (`State::SaveToBuffer`: RAM, devices, video state), the session NAND's game files at host level (`tmp`, `title`, `shared2` and the FS's `fst.bin`; Dolphin's own directory listing skips names over 12 characters, and Brawl caches its font in `/tmp/font_latin1.arc`), the map of GPU-written granules, and the inputs of K-1. zstd level 3 with a 128 MiB window.
3. Sent on channel 2: a 36-byte header, then 256 KiB chunks, a few in flight at a time. The joiner tells every player each tenth of the image it has (`image_progress`), and every machine shows it as a grey line in the chat window: "Getting the game from <host> (30.2 MB)" and "Getting the game: 40%" on the joiner, "Sending the game to <joiner>: 40%" on the sender, "<joiner> is getting the game: 40%" on the others, then "<joiner> is in the game." or "could not join." (2026-10-14: a UK host sat 49 s on a frozen REX room with nothing on screen and quit). The chat window is drawn on the game's frames, so while the game waits the video thread shows the last frame again about 30 times a second (as a paused replay does) and the overlay keeps drawing; without it the progress lines froze with the game. With ENet's own window (64 KiB of reliable data in flight per peer) the image travelled at about 64 KiB per round trip: 2.5 MB/s US to US (29.4 MB in 11.7 s, measured in a room), 0.53 MB/s at 110 ms (22.5 MB in 42 s through netsim). From 2026-10-14 each machine raised the window to 1 MiB (20b97589), which was too much at once for a home uplink: IMPY#5 joining the user's REX room got stuck at 10 % for 13 s, then ENet dropped the link at 70 % ("could not join"). ENet has no congestion control of reliable data and resends a lost packet only after a timeout that doubles at each try, dropping the link once a try waits 10 s, however many later packets were acknowledged; and on the sequenced image channel nothing after a lost packet reaches the joiner. Now (`PaceSendWindow`, `ResendLost` in MachineSession.cpp) the window is a congestion window per peer: 64 KiB, doubling each round trip that used it, halved on a loss while the round trip is well above its lowest (a buffer filling) or on a quarter of a round trip resent (a rate limit with little buffer), then growing 16 KiB a round trip, up to 1 MiB; a packet unacknowledged for two round trips plus four deviations while the peer still answers is resent then (as TCP's RACK). `harness/tools/machine_join.py` times a REX TE 1.1.1 join (18 MB) through netsim; before / after: 16 Mbit/s with a 60 ms buffer at 40 ms, could not join / 13.1 s; 8 Mbit/s with 100 ms at 80 ms, could not join / 31.5 s; 16 Mbit/s with a 10 ms buffer, could not join / 15.7 s; 1 % loss at 40 ms, 0.9 s / 1.0 s; 110 ms, 2.2 s / 2.3 s; 5 % loss each way at 150 ms, 4.4 s / 9.9 s (the price of the loss rule). `PPR_MACHINE_FIXED_WINDOW=1` keeps the fixed window for comparisons, `PPR_MACHINE_CC_LOG=1` logs the window each round trip. On a jittery link (Wi-Fi) that window collapsed (2026-10-15): through netsim at 80 ms with pareto jitter of 25 ms each way the image took 82 s with the SD card's list sent unpaced, and paced the joiner gave up on the list (2.3 MB at 0.04 MB/s, 60 s); with normal jitter of 10 ms the list took 55 s and the image 16 s, and a 103.6 MB SD card difference had 35.5 MB after 600 s. ENet's first retransmission timeout is its mean round trip plus four deviations, and it updates the deviation with each acknowledgement, so a run of them arriving together (a transfer's, held up behind one slow packet) shrank it to a few ms and the next slow packet timed out with all sent after it: a third to a half of a round trip resent though the joiner had it, each counted a loss, while the mean round trip, which jitter keeps above its lowest, made every round trip look queued, so the window halved every round trip. It did so on a clean link too whenever a queue began, which is all that held back an SD card upload whose pace had climbed past the uplink. Now (`ResendLost`, `OnAck`, `InterceptAcks`) the session reads each acknowledgement before ENet does (ENet's intercept): a packet is resent as soon as the peer acknowledged one sent after it and it has been out that one's round trip plus a quarter of the link's lowest (TCP's RACK, RFC 8985), otherwise its first timeout is at least the highest round trip of the last 2 s plus a quarter; an acknowledgement that echoes an earlier send of a resent packet (ENet echoes each send's time) shows the resend was needless (Eifel, RFC 3522): it is no loss, and a cut whose losses all prove so is undone. "Queued" is the lowest of ENet's round trip over the last round trip instead of its value now. PaceSD (§6.5) judges a link by the lowest round trip of its last 100 ms instead of 500 ms, and a jittery one by the lowest of its last 3 s of readings, and its rate grows only while the rate, not ENet's window, holds the upload back. Before / after (REX's 19 MB image, from the host's "Sending the game" lines; the whole join in brackets, joiner start to playing): 16 Mbit/s with a 60 ms buffer at 40 ms, 13.4 s (20.0) / 10.7 s (19.6); 8 Mbit/s with 100 ms at 80 ms, 28.3 (37.6) / 21.3 (30.6); 16 Mbit/s with a 10 ms buffer, 16.0 (25.1) / 13.1 (24.6); 1 % loss at 40 ms, 1.1 (13.5) / 1.0 (10.0); 110 ms, 2.3 (14.5) / 2.3 (11.5); 5 % loss each way at 150 ms, 9.1 (21.1) / 8.3 (18.5); 80 ms with pareto 25, could not join / 24.0 (33.6), the list unpaced 82.2 (96.8) / 25.1 (34.6); 80 ms with normal 10, 16.0 (75.8) / 2.6 (11.5); the SD card's list in those two, 65 s (gave up) and 54.5 s / 3.7 s; the 103.6 MB SD card at 80 ms with normal 10, not done in 600 s / 48.3 s, at 40 ms without jitter 20.3 / 20.3 s. The pareto runs still resend a few hundred packets an image: netsim's own socket drops part of a burst at times. `PPR_MACHINE_CC_LOG=1` also logs the needless resends, RACK's and the cuts undone.

**GekkoNet's packets and ENet's throttle (2026-10-15, bug reports #2 and #4).** GekkoNet's packets go unsequenced (unreliable), and ENet drops unreliable packets itself when a round trip comes in more than twice its deviation above the last ones (`enet_peer_throttle`): on Wi-Fi, with the SD card's background stream on the same link, that could throw away a player's inputs while both games waited (in every freeze of #2/#4 both machines waited for the other's inputs at once). Now each session link keeps the throttle open (`PaceSendWindow`), and tells the peer to as well (`enet_peer_throttle_configure` at connect, so an older build stops throttling towards this one); `PPR_MACHINE_ENET_THROTTLE=1` keeps ENet's. Every 10 s each link's round trip, deviation, loss, throttle and window go in the log ("machine: link to player 2: ..."). Measured with machine_join.py at 80 ms with pareto jitter (25 ms), 2 minutes of play after a join, freezes of 250 ms or more (the machine image's wait left out): this build with the throttle open 21 freezes, 9.6 s, with ENet's 17, 9.0 s (no difference without other traffic on the link); 0.1.74 with the same card 24 freezes, 11 s, and with a card that differed (its background stream running) 45 freezes, 23 s: the stream on a playing link doubled the freezes, and a session no longer has one.
4. The joiner loads it with the video thread paused and the JIT blocks of all RAM erased, replaces its NAND game files, starts its snapshot ring with one snapshot (the players' rings end with K's state twice; without it the joiner could not roll back the first frame after K), and compares its RAM checksum with the requester's.

Measured on Brawl Minus at the main menu, on one PC: **29-48 MB compressed (185 MB raw), built in 260 ms, sent in 0.8-1.4 s, loaded in 200-430 ms**; then 0 mismatches over 1,600-3,600 compared frames, single and dual core. Over the internet at 10 Mbit/s the others would wait about 30 s.

Why joins desynced on the way there, for the record: the joiner's ring lacked K's second snapshot (a rollback in the first frame after K was skipped); the joiner lacked `/tmp/font_latin1.arc`, so the game rebuilt its font cache and the emulated NAND latency moved an IPC reply by 1.3 M cycles; the savestate's own NAND copy reverses directory order. Found by logging confirmed frames' device states, CoreTiming queues and NAND digests on every machine (`PPR_MACHINE_PARTS_AT`) and comparing them.

**Version 2 (planned): nobody stops.** The image is taken at an epoch K1 and sent while everyone plays on; the joiner replays K1..K2 from the inputs, unthrottled and unrendered, and is admitted at a second epoch K2 once it has caught up.

## 7. Security of the machine image

The machine image is the first thing in this project where **one player's machine loads data another player made into the emulator itself**. It must be evaluated and confirmed before release (user, 2026-10-12).

**What an image can do:**

| Part | Risk | Why |
|---|---|---|
| MEM1, MEM2, L1 | **Low** | Guest memory: the emulated console runs it. It can only do what any game disc could do in Dolphin: emulator escapes would be Dolphin bugs reachable by any disc. |
| NAND files | **Medium** | Paths and sizes come from the peer: path traversal (`../`), huge files, file counts. Validated (built): only `tmp/`, `title/`, `shared2/` and `fst.bin`; printable; no empty, `.` or `..` component; no `\` or `:`; at most 4096 entries; sizes within the image. `fst.bin` (the FS's own metadata) is then parsed by the FS: part of the audit. |
| Device state (`DoState`) | **High** | Dolphin's savestate loader trusts its input: counts read from the stream size vectors and index arrays, pointers are rebuilt from offsets, enum values select code paths. A crafted state could corrupt Dolphin's own memory: code execution on the joiner's PC. |

**Plan** (progress and findings: `docs/brawl-mods-security.md`):

0. **The other players vouch for the image** (built): every player computes the image's digest at K themselves (their machines are identical there) and the joiner loads only an image whose digest every player sent. A crafted image needs every other player to collude; a room of two trusts its host.
1. **Audit** every `DoState` reachable from `State::DoState` for the session's configuration (Wii, the pinned devices): list each value read from the stream that sizes an allocation, indexes an array, selects a type, or becomes a pointer or length. Record the list in `docs/brawl-mods-security.md`.
2. **Harden** the load: `PointerWrap` read mode checks every read against the buffer end (it does; verify) and fails the whole load on the first error; every count and index found in step 1 is checked against its real bound; allocations from stream sizes are capped. A failed load leaves the joiner on a fresh boot with "Could not load the game from <host>".
3. **Fuzz** the hardened loader: mutate real images (byte flips, length fields, truncation, splices between images) and load them in a harness Dolphin, with ASan in a dedicated build. Exit criterion: no crash and no sanitizer report in a long run (**default** 24 hours across the configs of step 1).
4. **Limit who sends:** only the session host, which the room's host is (or the next host). The joiner can see who it is getting the game from. In a 3-4 player room the other members' confirmed checksums after the plug-in show whether the image was honest (a lying host desyncs from everyone else).
5. **Fallback:** if step 3 is not met before release, images are only accepted in **private rooms from players in the joiner's friends list** (**default**), and public rooms use input replay from boot (slow but safe) until it is.

Tested with Qt Dolphins: kicked, closed in 1.3 s; refused again with the wait; Leave twice, closed in 2 s with no error and the host's room shows only the host.
- **An open Dolphin without a game (fixed 2026-10-13, all of Brawl Online):** Play, a room's Join and Other Games used to need the player to close a netplay Dolphin that was open without a game (after its game window closed, or Configure). The launcher now writes `quit-if-idle.json` in its online folder; a Dolphin without a game closes (MainWindow), one in a game ignores it, and the launcher goes on after it closed (or as before, after 4 s, when it is in a game). Since 2026-10-18 Dolphin answers in `quit-if-idle-answer.json` (`closing` or `in-game`), so a game is known at once, and a room click, an invite, Create room and Play unranked/ranked ask it too instead of trusting `game-status.json`, which stays fresh after Stop (docs/rooms-protocol.md §5).
- **The GameCube adapter in a session (fixed 2026-10-13):** a session's config layer makes every port a standard controller and reads the adapter itself, but the adapter was polled only while a port's *current* SI device was the adapter: an adapter player sent nothing. It is now polled while the player's own setting (the base layer) uses it.
- **Dolphin's Controllers settings in a session (fixed 2026-10-14):** they wrote over the session's layer while a game ran (`Config::SetBaseOrCurrent` writes the running game's layer when another layer is active), so a port's type changed there changed this machine's emulated hardware: prod, ONYX#210 (an adapter player) set port 1 to the GameCube adapter in their REX TE room, and every machine image they sent after it failed to load on the joiner ("the machine image's state does not load": SI's device type, refused for a machine image), four joins in a row, the joiner's Dolphin closing each time. In a session the GameCube and Wii Remote panes now show and change the player's own setup (the base layer, which `PickLocal` reads every 30 frames), and the emulated hardware ignores any write over the session's layer: SI keeps standard controllers, the Wii Remotes stay emulated and the balance board none (its source was the player's own and is in every state). A failed state load now says after which marker and at which byte (`State::LoadFromBuffer`), and every player logs the reason in a leaver's `leave` ("player 2 left: ..."). Reproduced and checked with `harness/tools/machine_join.py --host-config Dolphin.Core.SIDevice0=7` (the harness's `config_set` takes `layer: current`): before, "could not join ... (after "VideoInterface" ...)"; after, 2 of 2 joined, 0 desyncs.
- **An adapter controller's origin (2026-10-14):** the session's ports are standard controllers with a perfectly centered origin, so a controller whose sticks or triggers rest off center reached less far on one side: the likely cause of a staging report (the Mac, adapter: C-stick smashes missed most of the time, fine in P+), not yet confirmed by the log below. Dolphin's adapter device tells the game the controller's own origin (its state when plugged in); the session now moves that origin into the values it sends (`AdapterInput`), which the game then sees the same way. Every 600 frames with C-stick use, the log says how often the C-stick was pushed in the adapter's reads and in the frames' samples, the longest gap between samples and the adapter's rate; the controller's rest position is logged when it is picked.
- **Build hash v2:** the disc's part is the SHA-1 of the disc's contents (`DolphinTool verify -a sha1`, 2.8 s for a 4.7 GB ISO here), not of the file: an ISO and an RVZ of the same disc are the same build, and the hash is the published dump hash. The launcher stays SHA-256 of the file. Each part's hash is kept (`parts`).
- **Build hash v3 (2026-10-14, the user's decision):** of the SD card only whether the game has one counts (`sd:card` or `sd:-`): everyone in a room plays the host's card (§6.5), so a card written to (a mod's settings, played solo or in another room) still joins any room of the same mod and stays in sync.
