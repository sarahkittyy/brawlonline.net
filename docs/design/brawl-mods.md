# Brawl Mods: whole-game rollback for any build (design)

_2026-10-12. Branch `brawl-mods`. The user's decisions from the conversation of 2026-10-12, plus defaults chosen without asking (marked **default**: say if one is wrong). Nothing here changes the P+ online modes (Direct, Unranked, Ranked, rooms): they keep their in-game menus and gameplay-only rollback._

---

## 1. What it is

A second way to play online, for every build of Brawl that is not the P+ release we ship, and for other GameCube and Wii games where it works:

- **The whole game is rolled back, from boot.** Every player runs the same machine. The menus are shared: everyone sees the same main menu, character select and stage select, and anyone's controller can drive them, as when friends sit at one console. Nothing in the game is ours, so nothing in the game has to be ported per mod.
- **Plug in and out like a controller at a LAN.** A friend who joins gets the running game and their controller is plugged into the next port at an agreed frame. A player who leaves is unplugged the same way. Everyone else keeps playing.
- **The launcher holds the room.** The game shows no room UI. The launcher shows who is in the room, the slots, public or private, kick, and the build everyone must have.

Why: Brawl Minus, REX, vanilla Brawl and other mods have no online play with rollback. Our P+ menus are the best way to play P+, but they cannot follow every mod (tested on Brawl Minus 5.1, 2026-10-12: the plugin loads, the WITH FRIENDS page crashes, and the P+-only state it reads does not exist). Whole-game rollback needs no knowledge of the game.

## 3. How it works, end to end

```
 Launcher (Brawl Mods tab)                Dolphin (one per player)                   mm (rooms, signaling)
 ─────────────────────────                ──────────────────────────                 ─────────────────────
 pick a build, Host ──launch──────────▶   boot the build, solo session  ──hello────▶ room (kind "mods", build hash)
 room window ◀──local control channel──▶  room client, chat overlay      ◀─room-state─
                                          P2P ENet host (session)       ──session ticket (from P2P port)──▶
 friend: Join KFQB ──launch──────────▶    boot nothing yet; join room  ◀─peers' endpoints───
                                          ◀═══════ P2P: machine image, inputs, GekkoNet ═══════▶
                                          plugged in at frame K; play
```

- **Dolphin is the room client**, as it is for P+ rooms today (`Online/Rooms.cpp`, one online connection per account). The launcher talks to the running Dolphin through a **local control channel**: a loopback TCP connection with a random token, both written to `<User>/Online/control.json` (**default**; it replaces file polling for anything live). Room clicks from the launcher's public list reach Dolphin the same way (or through Dolphin's command line when it is not running).
- **Host:** the launcher starts Dolphin with the build and `--mods-room=host[,private]`. Dolphin boots the build, starts a session of one, opens the room on mm and reports it on the control channel; the launcher opens the room window.
- **Join:** the launcher starts Dolphin with `--mods-room=join:KFQB` (or tells the running one). Dolphin joins the room (mm checks the build hash), registers its P2P endpoint, receives the members' endpoints, connects P2P, asks the session host for the machine, loads it, catches up, and is plugged in.
- **Built (2026-10-12), Dolphin's side** (`Online/ModsRoom.cpp`): Dolphin is armed before boot from `PPR_MODS_ROOM` (JSON: `{"host": true, "build": {hash, name}, "public", "controller", "delay", "port"}` or `{"join": "KFQB", ...}`; the command line and the control channel come with the launcher, phase 7). The room's messages go over the Rooms thread's online connection (as chat's do): `mods-create` or `mods-join` once it is up, and again on a new connection (the same code and slot; a new room if it is gone and this player's session still runs). Every `mods-state` becomes the session's members (`Machine::SetRoom`): a new member is a joiner (late); a member who left the room is unplugged when its link drops, or at once when someone else has its slot (GekkoNet drops the old player, the new one is admitted at the next epoch). While mm has no endpoint for this player, the session's own UDP socket sends `mods-endpoint` (with the LAN address, as Slippi's matchmaking finds it); a peer with this player's public address is reached at its LAN one. A peer's `hello` is taken only from one of its addresses, and says whether its sender plays (a joiner learns the session's players from that). Leaving or being removed from the room ends the session there. Harness: `mods_status`, `mods_request` (leave, kick, slot, public).
- **The launcher's hand-off (built)** is two files in Dolphin's online folder, as for P+ rooms (`docs/rooms-protocol.md` §5) rather than a socket: `mods-request.json` in (`{version: 1, id, op: "leave" | "kick" | "slot" | "public" | "controller" | "configure", slot, open, public, controller, createdAt}`; read and deleted within half a second) and `mods-room.json` out (`{version: 1, kind, state: "joining" | "in" | "left", error, room: {code, public, build, host, you, slots: [{slot, open, player: {displayName, connectCode, controller, connected}}]}, session: {phase, error, players, epoch, frame, slot, peers: [{slot, connected, rttMs}]}, input: {controller, index, device, plugged, real}, lastRequest: {id, result, error}, pid, updatedAt}`; on every change and at least every 5 s). Hosting and joining start Dolphin with `--mods-room <json>` (the JSON of `PPR_MODS_ROOM`).

## 4. The build

A build is what the player picks once in the Brawl Mods tab ("Add a build"):

| Part | What | Hash |
|---|---|---|
| Disc | The game's disc image (Brawl: `RSBE01`) | The game ID, revision and Dolphin's disc hash (the same hash the P+ disc check uses) |
| Launcher | Optional `.dol` booted instead of the disc (Minus Launcher, P+ launchers). Riivolution is a later option | SHA-256 of the file |
| SD card | Optional: an image (`sd.raw`) or a folder Dolphin syncs into an image | SHA-256 over the card's **files** (path, size, contents, sorted), not the raw image, so a card rebuilt from the same files hashes the same |
| Settings that change what the game computes | Dolphin's emulation settings a session pins anyway (§6.8) | not part of the hash: the session forces them |

- **Build hash** = SHA-256 of the three parts above; shown as 8 hex digits (`3f9a1c07`), full on hover.
- **Known builds** come from a small table in the launcher (`launcher/src/mods/known_builds.ts`): hash → name, version, homepage. The table only names; unknown builds play the same way.
- **The SD card is read-only during a session.** Writes are refused (the game sees a write-protected card) (**default**; Nyx's fork does the same). Saves on the NAND work (§6.5).
- Hashing a 2 GB image file by file takes a few seconds; the launcher caches the result by (path, size, mtime).

## 5. Rooms (server)

Mod rooms live next to P+ rooms in mm (`server/crates/mm/src/mod_rooms.rs`, messages in `server/crates/common/src/mods.rs`), on the same online connection after `hello`, with their own messages rather than a kind on `room-create` (they share nothing with P+ rooms but slots and codes). A player is in at most one room: creating or joining a mod room leaves their P+ room.

| | P+ rooms | Mod rooms |
|---|---|---|
| Create | `room-create {public, ruleset}` | `mods-create {build: {hash, name}, public, controller}` (`controller` is `"gc"` or `"wiimote"`) |
| Join | anyone | `mods-join {code, build: {hash}, controller}`: only with the same `build.hash` (`mods-error` "You need <name> (<hash>) to join.") |
| Ruleset, rules, stages, sets, ready, teams | yes | **none** |
| Start | when every open slot is ready | **never**: the host's session runs from creation; members plug in |
| Slots | open/close, kick by closing | `mods-slot {slot, open}`, `mods-kick {slot}` (host); `mods-public {public}`; `mods-leave`. Slot moves (`docs` §9 phase 3) later |
| Controller | | `mods-controller {controller}` (any member): what it plays with now, switched mid-game; every member gets the new `mods-state` (nothing when it is the same) |
| State | `room-state` | `mods-state {code, public, build, host, you, token, slots: [{slot, open, player?: {displayName, connectCode, controller, endpoint}}]}` to every member after every change; `mods-left` when the receiver is out (left, kicked, slot closed) |
| Public list | `GET /v1/rooms` | the same response's `modRooms`: code, build, host name, players, open slots (fuller first) |
| Session signaling | room ticket at the start | **`mods-endpoint {token}`**: the member's session sends its `mods-state` token from its P2P UDP port's address on a connection of its own (no `hello`); mm records the address it came from as the member's `endpoint`, answers `mods-endpoint-resp` (with `error` for an unknown token) and closes it. Every member gets the new `mods-state` |

mm stays the only server involved. No game data goes through it: the machine image and inputs are P2P. Room codes are never a live P+ room's code. Rate limits as for P+ rooms. Kicked players cannot rejoin the same room for 10 minutes (**default**). An empty room closes; a host who leaves hands the room to the member who has been in it longest.

## 6. Dolphin

### 6.1 The frame boundary

Snapshots are taken, and inputs change, at a **frame boundary** that must fall on exactly the same instruction on every machine.

- **Brawl builds:** Brawl's main-loop hook (`0x80017504`, `BrawlbackGekkoNetFrameEnd`), as the whole-machine path does today. Checked clean against P+'s and Brawl Minus's codesets (2026-10-12). Every Brawl build runs this `main.dol`.
- **Other games (built 2026-10-13):** the start of each **VI field** (`Machine::OnViBoundary`). The VI's new-field event sets `Machine::g_vi_boundary`, and `CoreTiming::Advance` runs the boundary once its events and the exceptions they raised are done: between two JIT blocks, where a snapshot can be saved and loaded, and where events are serviced at the same instruction on every machine (they already were: every interrupt depends on it). This is the placement of Nyx's fork (Brawlback-Team/Project-Plus-Dolphin, `Dolphin-Wide-Rollback`, "VI New Field", `RunPendingVIBoundary` at the end of `Advance`); no per-instruction guard was needed. The session option `"boundary"` is `"auto"` (default: Brawl's hook for a Brawl build, `IsBrawlGameId`: a disc ID starting `RSB` or a launcher's `ID-...`; the VI field for anything else), `"brawl"` or `"vi"`. When the boundary waits for the players and must give the CPU back (a pause or stop), every CPU core (Jit64, JitArm64, the interpreters) now leaves right after `Advance` instead of running a block, and the next `Advance` takes the same boundary again.
- **What the VI boundary needed besides** (found with New Super Mario Bros. Wii, `SMNE01`):
  - **Brawl's HLE hooks only for Brawl.** They were installed at fixed addresses for every game (`HLE::PatchFixedFunctions`): in any other game they replaced whatever instruction sits there.
  - **The guest's `pc` and `npc` (and the `lwarx` reservation) in a whole-machine snapshot.** Brawl's hook always resumes at its own address, so they were never saved; at a VI boundary the CPU stands anywhere.
  - **A load must not schedule events.** Restoring the video thread's state goes through `AsyncRequests`, whose `QueueEvent` called `Fifo::RunGpu`, which in deterministic dual core schedules the GPU-sync event when syncing is suspended: an event the saved state did not have, and its `ForceExceptionCheck` cut CoreTiming's slice after the load had restored it while the restored downcount stayed, so `slice - downcount` (the cycles run) went negative and time jumped back ~10,500 cycles. Brawl's loop top happens to be a point where this did not show. Now no `RunGpu` from `AsyncRequests` during a whole-machine snapshot's DoState (the video thread is only woken), and a load restores the slice length with the downcount.
  - **The emulated Bluetooth stack's pending requests**: saving rebuilt them from guest RAM (crashed when the RAM there no longer held an ioctlv); saving now writes only their address, and loading refuses a request that is not one (a machine image is hostile data: it read past an empty vector).
  - **The desync checksum counts what changed, not what was written.** A store of the bytes already there marks a granule written on one run of a frame and not on another (same state, other granules marked: thousands at a level load). `RollbackManager` keeps a shadow of RAM as of the newest save (taken with the base snapshot, so a joiner's is its image; updated by every save and every load's restored granules) and the checksum covers only the written granules whose bytes differ from it.
- **Across hosts (NSMB Wii, this PC on Jit64 hosting, the M4 Mac on JitArm64 joining, both on Wii Remotes, LAN):** the first run had a desync every few thousand frames, always the same 13 granules of float arrays holding a NaN: `0x7fc00000` on the PC, `0xffc00000` on the Mac. A NaN an operation generates (no input is a NaN) is negative on arm64 with FPCR.AH set, which Dolphin sets in non-IEEE mode on FEAT_AFP CPUs (§6.6), and positive on PowerPC (Jit64 writes PowerPC's default NaN). JitArm64's accurate-NaN paths left that NaN to the hardware; now the scalar arithmetic path checks its last input too and clears the generated NaN's sign (an integer `BIC` of the top bit of each 16-bit lane: under AH, `FABS` leaves NaNs alone), the paired path does the same for each NaN lane before it puts input NaNs back, and `ps_sum0/1` compute their sum aside and fix it the same way. After: 8 minutes, the last 16,334 frames compared with 0 mismatches; one single-frame desync at frame 9,516 (one granule: four increasing ~4.7M-tick values on the Mac, zeros on the PC, during a load; the machines agreed again at once). Open.
- **Results (2026-10-13, this PC, Jit64, dual core):** NSMB Wii sync test, distance 6 (every frame rolled back 6 and re-run), random Wii Remote + Nunchuk input, 5 minutes: 13,889 frames from boot through the menus into World 1, 19 desyncs, all in the first 637 frames after boot (granules the first run marks written and a re-run does not, bytes the same; a room's host boots alone, so nothing compares those frames: open). A room through a local backend, host and a joiner (machine image, 4 s), both on Wii Remotes: 9,125 frames, 0 mismatches. Brawl Minus on Brawl's hook unchanged (sync test, 7,390 frames, 0 desyncs); Brawl Minus forced onto the VI boundary desynced before the load fixes (not re-run since).

### 6.2 Inputs

Inputs enter where the hardware does, so nothing depends on the game:

- **GameCube pads:** `SI_DeviceGCController::GetPadStatus` already asks netplay (`NetPlay_GetInput`). In a session every SI poll of frame F returns frame F's pad for that port.
- **Wii Remotes:** the emulated Bluetooth stack asks netplay once per Wii Remote update (`BTEmu.cpp`, `NetPlay_GetWiimoteData`, 200 Hz) with a `SerializedWiimoteState` (at most 31 bytes: buttons, acceleration, IR points, MotionPlus, extension). In a session every update of frame F uses frame F's state. Dolphin's netplay sends this state per update in lockstep, which stalls the CPU thread (Nyx disabled Wii Remotes for that reason); we latch it per frame instead, so it is predicted and rolled back like a pad.
- **One player, one port.** A player in slot N drives GameCube port N and Wii Remote N. Their input per frame (**default**, 48 bytes):

  | Bytes | Field |
  |---|---|
  | 0 | flags: bit 0 GC pad present, bit 1 Wii Remote connected |
  | 1-8 | GC pad: buttons (2), stick X/Y, C-stick X/Y, L, R |
  | 9 | Wii Remote state length (0-31) |
  | 10-40 | `SerializedWiimoteState::data` |
  | 41 | a membership request (§6.3): bit 7 admit, bits 0-1 the slot, bit 2 it plays a Wii Remote |
  | 42-47 | reserved, zero |

- **Plugging** is the input itself (built 2026-10-12): every port is a standard controller and every Wii Remote an emulated one on every machine, whoever plays (so a joiner's machine is configured like everyone's). A port whose input lacks the GC flag answers as an empty port; a Wii Remote is connected exactly while its input says so (`WiimoteDevice::Activate`, checked at the start of every frame, the same frame on every machine; none connects at boot). A player who leaves gets GekkoNet's disconnected input (all zero) from the frame the others agreed on, so their controller is unplugged everywhere at once, as at a LAN.
- **Prediction:** a remote player's last confirmed input repeated (GekkoNet's), Wii Remote included.

### 6.3 Sessions and epochs

- **GekkoNet** carries inputs (fixed size, §6.2), as in the P+ paths. Its player count is fixed per session, so a session is a chain of **epochs**: a player joining ends the epoch at an agreed frame K and starts a new GekkoNet session at K with the new set of players. Frame numbers keep counting across epochs (the epoch's frame + GekkoNet's frame).
- **Leaving needs no epoch** (built): GekkoNet's disconnect claims agree on the last frame of the leaver's input, and the others play on with that controller unplugged. A claim carries the leaver's whole input queue (128 inputs of 48 bytes), so the session's limit for a GekkoNet packet is 16 KiB.
- **Agreeing on K** (built): the request travels in the input. The player who admits a joiner (the lowest slot that is playing) sets byte 41 of its input; the first frame F whose input carries it plans the epoch at **K = F + 10** (`EPOCH_LEAD`, more than GekkoNet's prediction window of 7). Nobody can run K before F's input is confirmed, so every machine plans the same K, and a request seen in a mispredicted input is planned again when the frame re-runs. GekkoNet gets a frame limit (`gekko_set_frame_limit`, added to our GekkoNet): it never advances into K but still rolls back earlier frames; when `gekko_confirmed_frame` (added) reaches K-1, every machine holds the same state at K. No proposal, acknowledgement or timeout race.
- **At K:** every player sends the requester a checksum of all its RAM at K (they agree: the players' machines at K are bit-identical, savestates included); the requester sends the joiner the machine image (§6.7), waits for the joiner's checksum of the loaded machine, and tells everyone the new set of players (`epoch_go`). Each starts a new GekkoNet session; the frames its input delay holds back repeat its input of K-1 (`gekko_set_local_delay_input`, added), so no controller unplugs for two frames. If the joiner's image does not load within 120 s, the players go on without it.
- **Transport:** the P2P ENet hosts and hole punching of `Online/Matchmaking.cpp`, with GekkoNet's adapter over them (as `GameplaySession` does). Channel 0: GekkoNet; channel 1: session control (JSON, small); channel 2: machine images (§6.7), rate-limited.
- **Pacing, time sync, presentation:** reused from the P+ gameplay session where they are not Brawl-specific (`CoreTimingManager::BeginRollbackBurst`, present pacing, audio clock waiting during resimulated passes).

### 6.4 Snapshots

`RollbackManager` in whole-machine mode (not region mode): MEM1, MEM2, the locked L1 cache and Dolphin's device state, saved incrementally (64-byte granules written since the last save). Measured on P+ (2026-10, Fox/Falco, distance 2): **0.90 ms per save, 1.57 ms per load**. The Brawl-specific parts of the path that exists today move behind the session: pads written into Brawl's `gfPadStatus` (replaced by §6.2), Brawl's desync checksums (replaced by §6.6), the Brawl frame counter.

### 6.5 NAND and SD

- **NAND:** the session runs on a temporary NAND, as Dolphin's netplay does. A rollback must also undo file writes: a **write journal** records each file's previous contents (or absence) at its first change after a snapshot; a load undoes the journal back to the snapshot's mark (**default**; Orca and Nyx do this, `IOS/FS/HostBackend/Journal.cpp`, GPL, ported with attribution). Saves made during the session are written back to the player's own NAND at the end only if the user ticks "Keep saves from this session" (**default** off).
- **Every player must boot with the same save.** Today each player's session NAND copies its own save of the game (`WiiRoot.cpp`), so players whose saves differ (unlocks) desync from boot. Open question 5.
- **SD:** read-only (§4).

### 6.6 Desyncs

- Each confirmed frame's checksum (GekkoNet compares them) is **CRC32 of the granules of MEM1 and MEM2 written in the frame, plus a rotating 1/360 slice of all RAM** (every byte is covered every 6 s), skipping granules the GPU writes. EFB and XFB copies stay on the GPU in a session (pinned), so nothing rendered reaches guest RAM: with copies to RAM, a dual-core re-run diverged where Brawl reads rendered pixels back (`docs/determinism-findings.md`).
- A desync shows "Desync detected, resyncing" in the OSD and the session host sends its machine to the players that differ (§6.7). Twice in a minute ends the session with "Desync: this build does not stay in sync online" (**default**).
- **What a rollback restores** (found with the sync test's diagnostics, 2026-10-12): a whole-machine snapshot carries, besides RAM and every device's state, the MSR and every SPR (the gameplay-only snapshots keep the 18 a game changes) and the instruction cache. The MSR's FP bit is the OS's lazy FPU switch: a re-run that took the FP-unavailable exception where the first run did not (its MSR was the thrown-away timeline's) ran the handler's cycles more, Brawl's main loop then counted two retraces instead of one, and the machines diverged. The JIT compiles through the instruction cache: after a scene change the thrown-away timeline had left a new module's code in lines where the restored memory holds the old one. About half of the 5-minute sync tests at distance 7 desynced before; 0 of 11 after (single and dual core).
- **Code caches at an epoch**: every player empties its instruction cache and drops its JIT blocks for RAM at the epoch's frame, the state a joiner starts in (a joiner's machine image carries neither).
- **The time base** a session's guest reads is the instruction's own, not its JIT block's start (Jit64 and JitArm64 `mftb`; upstream leaves it at the block's start for a game that breaks otherwise).
- **Across hosts (Windows x86-64 and an M4 Mac, 2026-10-13)**: a Mac joiner differed from the PC in ~800 granules from the epoch's first frame, the same with JIT or cached interpreter on the PC, any video backend. With the host's I/O log the two machines' inputs (MMIO reads, host writes) were the same up to one CPU store, and the instruction trace showed `ps_abs` leaving a negative value negative on the Mac. Brawl runs in non-IEEE mode (FPSCR.NI), for which Dolphin sets FPCR.AH (with FZ) on hosts with FEAT_AFP so that only outputs flush, as on x86; under AH, FABS and FNEG leave a NaN unchanged, and clang builds the mask 0x7FF...F as FNEG of all ones (a NaN): `Interpreter::ps_abs`, `std::copysign` in `fctiw`'s rounding and in `fres` (`Common::ApproximateReciprocal`) kept the sign, and the DVD's timing math had the same mask. Fixed: sign changes in the interpreter go through `Common::ClearSignBit`/`SetSignBit`/`FlipSignBit`/`CopySign` (integer ops on a mask the compiler cannot see through, `Common/FloatUtils.h`); the DVD's read scheduling runs in the host's default FPU mode (`Common::FPU::ScopedDefaultSIMDState`); and the build passes `-ffp-contract=off` to clang and gcc, as MSVC's `/fp:precise` already does (clang fuses `a * b + c` on arm64). A session on arm64 runs the cached interpreter (JitArm64 marks no dirty pages), so the interpreter's C++ is what has to agree with x86. After the fix the first frames after a Mac's join are the same granule for granule.
- **No host network in a session**: the next cross-host desync came ~2 minutes in, where the test's random inputs had reached Brawl's Wi-Fi menu: Nintendo Wi-Fi Connection's login asked for `naswii.nintendowifi.net` through `IOCTLV_SO_GETADDRINFO`, which Dolphin answers from the host's DNS on a worker thread, writing the answer into guest memory when the host has it (a frame later on the Mac, with other contents). The IP stack's vector ioctls now refuse like its plain ones under `Core::WantsDeterminism` (a session sets it), and so do WiiConnect24's network requests and its wall-clock scheduler. A session's guest has no network at all (also `docs/brawl-mods-security.md` §3).
- **One CPU core for everyone** (measured 2026-10-13): with both fixes a PC and a Mac on the cached interpreter stayed in sync for 16,180 frames; a PC on Jit64 against the Mac differed in ~35 granules from the first frame (saved FPRs in the OS thread contexts, and timebase values a few ticks apart: the JIT and the interpreter count cycles differently). Every machine in a session has to run the same core. But the cached interpreter runs Brawl at **35 frames/s** unthrottled on a Ryzen 7 9800X3D (Jit64: 600), below full speed before any rollback: a session on the cached interpreter is not playable. **Cross-play on the JITs (built 2026-10-13):** a session on arm64 runs JitArm64 (its fast stores mark dirty pages since a3fd38ff; a sync test on the M4 at distance 7: 5,864 frames, 0 desyncs) and pins FPRF, accurate NaNs and FMA on, so the two JITs and their interpreter fallbacks compute alike. Jit64 and JitArm64 then count the same cycles; what still differed, found with the I/O log's CoreTiming events and a probe at every block's entry (`PPR_MACHINE_IOLOG_BLOCKS`, with `PPR_MACHINE_IOLOG_BLOCK_DUMP` for the FPRs at chosen blocks): (1) the upper word of fctiwz's result, 0xFFFF0000 on the Mac: the arm64 emitter encoded 16-bit-lane ORR/BIC immediates as 32-bit lanes (upstream); (2) Jit64's mftb took the 32-bit conversion of a negative downcount as 64 bits (a time base 0x15555555 ahead); (3) ps1 after a double-precision result: the interpreter and JitArm64 keep the destination's ps1, Jit64 gave it the first source's with AVX three-operand ops (VMULSD d, a, b copies a's upper half: Jit64 differed between hosts with and without AVX), after a MOVSD from memory (zeroes it) and after write-only binds (whatever the host register held) in fneg/fabs/fnabs, fctiw and frsqrte. It shows only where the OS saves a thread's paired singles (psq_st of both halves into its OSContext), which every thread switch does. Fixed in Jit64. Result: a PC on Jit64 and an M4 Mac on JitArm64 stayed in sync for 10,751 frames, 0 mismatches. Seen on the way, not fixed: with some floating-point JIT categories turned off (`Debug.JitFloatingPointOff` and the like, a debugging setting) JitArm64 corrupted the heap during boot; with all of them on (the default) it never did.
- **Diagnostics across hosts**: `PPR_MACHINE_IOLOG=N` (with `PPR_MACHINE_DUMP_DIR`) writes the first N frames after the epoch: every MMIO read, every host write into guest RAM (and, with an interpreter core, every CPU store) with CRCs of the FPRs and GPRs; `-K` keeps the last K frames and writes them at the first desync; `PPR_MACHINE_IOLOG_REGS=FRAME:FIRST-LAST` adds the registers, the code around pc and each instruction the cached interpreter ran, for those events. Two machines' logs give the first instruction whose result differs.
- **Diagnostics** (sync test, `PPR_MACHINE_SESSION={"synctest":N}`): each re-run of a frame is compared with its first run: the granules that differ (`diag` in `machine_status`); `PPR_MACHINE_EVENT_TRACE=1` adds the CoreTiming events each pass ran with the guest CPU's pc, lr, r1 and registers at each (the first event where they differ); `PPR_MACHINE_STATE_CHECK=N` compares the whole state as an image carries it, and the NAND, at the start of every Nth frame's passes (`PPR_MACHINE_DUMP_DIR` keeps the first pair that differs); `PPR_MACHINE_NO_JIT_ERASE` and `PPR_MACHINE_JIT_CLEAR_EACH_PASS` change what a rollback does to the JIT (bisection only).

### 6.7 Joining: the machine image

**Built (2026-10-12), version 1: the players wait at K while the image travels.**

1. The joiner's Dolphin boots the same build, runs its first scBoot frame on its own and waits at the next loop top. That loop top starts a JIT block of its own, as the players' loop tops do, so the image loads at the same instruction (loaded in the middle of a longer block, the block's remaining cycles would be counted after the load).
2. The requester captures the image at K's loop top: Dolphin's savestate (`State::SaveToBuffer`: RAM, devices, video state), the session NAND's game files at host level (`tmp`, `title`, `shared2` and the FS's `fst.bin`; Dolphin's own directory listing skips names over 12 characters, and Brawl caches its font in `/tmp/font_latin1.arc`), the map of GPU-written granules, and the inputs of K-1. zstd level 3 with a 128 MiB window.
3. Sent on channel 2: a 36-byte header, then 256 KiB chunks, a few in flight at a time.
4. The joiner loads it with the video thread paused and the JIT blocks of all RAM erased, replaces its NAND game files, starts its snapshot ring with one snapshot (the players' rings end with K's state twice; without it the joiner could not roll back the first frame after K), and compares its RAM checksum with the requester's.

Measured on Brawl Minus at the main menu, on one PC: **29-48 MB compressed (185 MB raw), built in 260 ms, sent in 0.8-1.4 s, loaded in 200-430 ms**; then 0 mismatches over 1,600-3,600 compared frames, single and dual core. Over the internet at 10 Mbit/s the others would wait about 30 s.

Why joins desynced on the way there, for the record: the joiner's ring lacked K's second snapshot (a rollback in the first frame after K was skipped); the joiner lacked `/tmp/font_latin1.arc`, so the game rebuilt its font cache and the emulated NAND latency moved an IPC reply by 1.3 M cycles; the savestate's own NAND copy reverses directory order. Found by logging confirmed frames' device states, CoreTiming queues and NAND digests on every machine (`PPR_MACHINE_PARTS_AT`) and comparing them.

**Version 2 (planned): nobody stops.** The image is taken at an epoch K1 and sent while everyone plays on; the joiner replays K1..K2 from the inputs, unthrottled and unrendered, and is admitted at a second epoch K2 once it has caught up.

## 7. Security of the machine image

The machine image is the first thing in this project where **one player's machine loads data another player made into the emulator itself**. It must be evaluated and confirmed before release (user, 2026-10-12).

**What an image can do:**

| Part | Risk | Why |
|---|---|---|
| MEM1, MEM2, L1 | **Low** | Guest memory: the emulated console runs it. It can only do what any game disc could do in Dolphin: emulator escapes would be Dolphin bugs reachable by any disc. |
| NAND files | **Medium** | Paths and sizes come from the peer: path traversal (`../`), huge files, file counts. Validated (built): only `tmp/`, `title/`, `shared2/` and `fst.bin`; printable; no empty, `.` or `..` component; no `\` or `:`; at most 4096 entries; sizes within the image. `fst.bin` (the FS's own metadata) is then parsed by the FS: part of the audit. |
| Device state (`DoState`) | **High** | Dolphin's savestate loader trusts its input: counts read from the stream size vectors and index arrays, pointers are rebuilt from offsets, enum values select code paths. A crafted state could corrupt Dolphin's own memory: code execution on the joiner's PC. |

**Plan** (progress and findings: `docs/brawl-mods-security.md`):

0. **The other players vouch for the image** (built): every player computes the image's digest at K themselves (their machines are identical there) and the joiner loads only an image whose digest every player sent. A crafted image needs every other player to collude; a room of two trusts its host.
1. **Audit** every `DoState` reachable from `State::DoState` for the session's configuration (Wii, the pinned devices): list each value read from the stream that sizes an allocation, indexes an array, selects a type, or becomes a pointer or length. Record the list in `docs/brawl-mods-security.md`.
2. **Harden** the load: `PointerWrap` read mode checks every read against the buffer end (it does; verify) and fails the whole load on the first error; every count and index found in step 1 is checked against its real bound; allocations from stream sizes are capped. A failed load leaves the joiner on a fresh boot with "Could not load the game from <host>".
3. **Fuzz** the hardened loader: mutate real images (byte flips, length fields, truncation, splices between images) and load them in a harness Dolphin, with ASan in a dedicated build. Exit criterion: no crash and no sanitizer report in a long run (**default** 24 hours across the configs of step 1).
4. **Limit who sends:** only the session host, which the room's host is (or the next host). The joiner can see who it is getting the game from. In a 3-4 player room the other members' confirmed checksums after the plug-in show whether the image was honest (a lying host desyncs from everyone else).
5. **Fallback:** if step 3 is not met before release, images are only accepted in **private rooms from players in the joiner's friends list** (**default**), and public rooms use input replay from boot (slow but safe) until it is.
