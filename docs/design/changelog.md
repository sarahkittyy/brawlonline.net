# Launcher changelogs ("patch notes")

Sarah's board, 2026-11-25: "i wonder if we can implement a changelog system for patches from now on. like, before i push, i set up a changelog to go out with the launcher ... a one-time popup on the launcher after update, they x it out and don't see it again. changelog buttons can come later. we can store a log of past changelogs on the server, but we don't need to create the ui to serve the history yet, just the latest one on update." The first version had a web editor on brawlonline.net; she then asked for it in the agent board instead: "copy the code for the markdown editor into the agent board ... the editing, the copy-paste of images / file upload, and the preview split ... it saves my changelog persistently even when i reload the tab or move to other machines / browsers. any media copy-pasted in / uploaded stays local to my agent board server machine. when i push to main from the kanban board, the changelog goes with it. there's also a checkbox that says "show on staging" that's on by default and means every staging run shows that popup with the current changelog cache every single time."

## Writing one (the agent board)

**Patch notes** in the board's header (`D:\code\agent-board`, `lib/patchnotes.js`) opens the editor: Markdown on the left, the launcher's popup on the right.

- The draft is kept on the board's server (`data/patch-notes/draft.json`) as it is typed, so a reload, another browser or another device on the tailnet shows the same draft. A save over a newer version from another tab is refused and offers "Load that version / Keep mine".
- Pictures and videos: paste, drop, or **Upload image or video**. They stay on the board's PC (`data/patch-notes/media/`) under the name accounts gives uploads (the first 20 hex of the content's SHA-256 and the type's extension), and the Markdown points at `/blog/media/<name>`, the address they will have on brawlonline.net. The board serves that address itself, so the Markdown is the same on both. PNG/JPEG/BMP screenshots become WebP when that is smaller (at most 2400 px wide), as in the blog editor. At most 95 MB per file.
- The preview is accounts' own renderer (`pp-admin changelog render`, the staging build's admin tool or the checkout's), in a box like the launcher's popup. Before a staging build has this tool, the preview says to build staging.
- The Markdown is the blog's (docs/design/blog.md §2): a `#` heading is the popup's big heading, an image alone in its paragraph is a figure with its `[caption]`, `.mp4`/`.webm`/`.mov` are videos, raw HTML shows as text.

## Shipping it (Push to main)

**Push to main** (in the board's Changelog drawer) first publishes the patch notes on prod: `ssh debian@sarahvps2 sudo pp-admin changelog publish`, with the Markdown and every picture it shows as JSON on stdin. pp-admin writes the pictures into the blog's media folder (`BLOG_MEDIA_DIR`, `/var/lib/ppserver/blog-media`, mode 0644 so accounts reads them) and adds a `changelogs` row. Then it pushes. If publishing fails, nothing is pushed. If the push fails after publishing, pushing again doesn't publish the same text twice. After a push that carried them, the draft is kept in `data/patch-notes/history/` and the editor starts empty. An empty draft publishes nothing: that release has no popup. The push's confirm says which.

Publishing before the push matters: a launcher shows a changelog only if it was published before that launcher was built (below), and the release is built after the push.

## Staging ("Show on staging", on by default)

Each staging run from the board (▶ Windows, ▶ Mac, Run 2v2) first runs `staging.py admin changelog publish --every-start` with the draft (or `clear-every-start` with the box off or the draft empty). That puts it on the staging server as an `every_start` changelog, which replaces the last one and comes ahead of the others, and every test-mode launcher (staging's) shows it at every start, whatever it showed before. This step never fails the run; what went wrong is in the run's log. Prod never has an every-start changelog.

## What players see

After an update the launcher's main screen opens the patch notes in a popup over the page. The X (or Esc) closes it for good; a click beside it doesn't close it (a click in the launcher as it opens would lose it). Links open in the browser.

The popup is a feed (Sarah's board, 2026-11-26: "patch notes in the launcher, both with the new credits button, and the popup, should show in a row. we should only render the ones that fit on screen ... and only load more if you scroll. the top edge should stay where it is now and it should scroll like a vertical feed in the middle of your screen ... you should be able to scroll anywhere ... it could be one big vertical popup that scrolls inside itself"): every release's changelog, newest first, a thin line between two, in one popup (`changelog_dialog_view.tsx`, 600 px wide).

- Its top edge stays 32 px below the window's top, where a tall popup's always was; it grows downwards as changelogs come in, down to 32 px above the bottom, then scrolls inside itself.
- The wheel scrolls it anywhere over the window, beside the popup too, and the arrow / Page keys and Space scroll it while the focus isn't in it.
- It asks for two changelogs at a time (`changelog_feed.ts`, `GET /v1/changelogs`), and for the next two only while its end is less than 300 px below the bottom of the popup, once its pictures have loaded (their height is known only then). So it shows what fits, usually the newest two or three, and the rest as you scroll. A failed request stops the feed there until the popup opens again.
- The X stays in the popup's top right corner, outside the scrolling part, so it's there however far down you are. The text leaves room for it on the right, so nothing scrolls under it.

Exactly when:

- At each start the main process compares its version with the one that ran last (`lastRunVersion` in Settings, `main/changelog_version.ts`). A different one is an update and sets `changelogPending`. The first start of the release that brings changelogs has no `lastRunVersion`: it counts as an update unless the launcher has no settings at all (a new install, which shows nothing).
- With `changelogPending`, the page (`lib/changelog/changelog_dialog.tsx`, mounted with the main screen, so after setup or login) asks once for the feed's first page of the changelogs published before this launcher was built (`GET /v1/changelogs?before=<__DATE__>`). It opens the popup when the newest of them was published after the last one this launcher showed (`changelogSeenAt`); otherwise it clears `changelogPending`. Closing the popup clears it and stores that newest one's publish time in `changelogSeenAt`. Offline or a failed request: it asks again at the next start.
- A test-mode launcher asks at every start, and an `everyStart` changelog opens every time without being stored as seen.
- So (Sarah's board, 2026-11-26: "if i eventually push 0.2.10, and don't provide patch notes, people who update from 0.2.8 straight to .10 should still see the 0.2.9 patch notes, but people who already saw the 0.2.9 patch notes don't need to see anything new"): a release without patch notes shows the last ones to a launcher that hasn't seen them and nothing to one that has. A launcher that skipped releases sees every changelog since, the newest first. One published for a release still building doesn't show on the release before it, and doesn't hide the ones before it either (the old `latest` check saw only the newest, so a launcher that started after the next release's notes were published but before that release came out never saw its own).

**Settings > Changelog** (above Help; Sarah's board, 2026-11-26: "in settings, above "help", there should be "changelog". clicking it doesn't open a new page, it just makes the latest patch changelog popup appear.") asks for the feed's first page when clicked and opens the same popup over Settings (`lib/changelog/latest_changelog.tsx`, mounted at the root in `app/create.tsx`, as the startup one lives with the main screen). It starts with whatever is newest, without the build-time check, and closing it stores nothing, so the popup after the next update still comes. None published is a "No changelog yet." toast; a failed request is the usual error toast. Settings' entries can be such actions (`SettingAction` in `pages/settings/types.ts`): a button, no page or route.

The page cleans the server's HTML once more (`changelog_html.ts`): only the elements and attributes the blog's renderer writes, pictures and videos only from the accounts server, links absolute and opened outside.

## Discord (#updates)

Sarah's board, 2026-11-26: "i want to have the brawlonline bot upload my patch notes to #updates on discord automatically, so i don't have to write them twice ... we would have to strip all the icons, definitely remove a lot of whitespace, and maybe put all the images attached at the bottom."

The Discord bot (`D:/code/rust/brawlonline-bot`, its README "patch notes") posts each changelog in #updates once the launcher release that shows it is out: every 2 minutes it reads the release feed's `releaseDate` (`/updates/launcher/latest.yml`) and the feed's changelogs published before it (`GET /v1/changelogs?before=`, the launcher's own rule), and posts the ones it hasn't. It uses the `markdown` of each: the pictures alone in a paragraph attached under the text, the icons in lines of text dropped, blank lines only before headings, the board's mentions (below) as pings of their Discord accounts, `@Name` as a mention of the member of that name. Nothing changes in the board: publishing then pushing as above is all it takes. `/patchnotes preview|post [id]` (Discord admins) show or post one by hand.

## Mentions

Sarah's board, 2026-11-26: "i would love if @ on the kanban board let me search through users on both platforms. A custom kanban-only sort of token / syntax where I can specify a user as either discord, brawl online, or both ... in the launcher patch notes, the users would have their icons and badges and main and you could click on them to see their profile, hover to see their mini profile, and right click them. and when the same patch notes went out to discord, it would mention all the usernames that have discord attached. names that have no discord, mentioned on discord, show as just @their_brawl_online_username, plaintext. names that have no known brawlonline account, on brawlonline's patch notes, just show @plain_discord_username."

**The token.** A mention is written in the Markdown as

```text
@{sarahkitty bo:SARA#694 dc:123456789012345678}   both
@{sarahkitty bo:SARA#694}                         Brawl Online only
@{milla dc:61305312321208320}                     Discord only
```

`bo:` is a connect code, `dc:` a Discord user id (17 to 20 digits), each at most once, at least one of them, after the label. The label is what shows where nothing better is known: the Brawl Online name, or for a Discord-only one the Discord username. Anything else in braces is text. It is nothing in Markdown, so every reader handles it before the Markdown: accounts (`accounts/src/mentions.rs`), the bot (`parse_token` in its `patchnotes.rs`) and the board (`atParse`) read it the same way. Written by hand it works the same; the autocomplete just writes it for you.

**Writing them (the board).** In the Patch notes editor, `@` and two letters opens a list under the `@`: Brawl Online accounts by name or code (`SARA`, `sara#6`) and members of the brawlonline.net Discord server by username, display name or server nickname, at most 10, the closest first (a whole name or code, then the start of one, the start of a word, anywhere in it). The board keeps both lists and searches them itself, so typing costs nothing: prod's accounts (`ssh … sudo pp-admin user directory`, before that pp-admin is deployed `pp-admin user list`) and the server's members (`lib/discord_members.py`, run on the bot's VPS with the bot's token, which stays there), read again when 10 minutes old and kept in `data/mentions.json`. Both are reads.

- One person on both sides is one row: a Brawl Online account whose profile's Discord username is a member's (`link: profile`), or an account and a member with the very same name (`same name?` beside it: nobody linked them, Sarah judges). Such a row has **Both | Brawl Online | Discord** (←/→), Both by default.
- A row with one side has **+ Discord** / **+ Brawl Online** (→): it writes that mention followed by `@`, and what is typed after it lists only the other side's people; picking one makes the two one mention.
- Enter or Tab writes the highlighted row, Esc closes the list (not the overlay). Up to two spaces in what is typed are allowed (`@The Doc`); a typed text with a space that names nobody closes the list, as it's just prose.

**The preview** shows a Brawl Online mention as the account's name now, bold (wavy underline: no such account on prod), with a blue dot after it when it pings someone on Discord; a Discord-only one is plain text with a dotted underline. Hovering one says who it is on each side and what each place shows.

**Launchers.** The feed (`/v1/changelogs`, `/latest`) renders each mention as `<span class="mention" data-uid data-code data-discord>@name</span>`: `data-uid` and the player's name now (the label is only for a code nobody has, or a banned player) for a Brawl Online one, and lists those players in the changelog's `mentions` (uid, name, code and their name tag: the flag and main they show, the main icon and badges an admin gave). The popup puts the launcher's own name in each such span (`changelog_body.tsx`): main icon, flag, badges (those for the profile) and the bold name, which opens their profile, shows the hover card and has the right-click menu, as names do everywhere. A Discord-only one, or a code nobody has, stays plain `@label`. A launcher from before this sees the span's text, `@name`. In code (`` `...` ``) a token stays as written.

**Discord.** The bot pings the Discord account of each mention (`<@id>`, when that member is on the server); one without a Discord account, or whose member left, is plain `@label`, never guessed at as a member's name. `@Name` written by hand still pings as before. `/patchnotes preview` lists every mention and what it became.

## EmissaryRecomp

Sarah's board, 2026-11-26: "it's probably right that we have recomp patch notes separate. this requires design in the kanban board for where i put them, as well as design in the launcher-- it'd be weird if i did a push of both and they got two popups. i also think it'd be weird if there was a popup each recomp update for even the people that didn't use it." Then: "i like the ideas for the emissary patch notes in the kanban board and all that. made a new #emissary-updates channel that the bot should post to."

- **Board.** The Patch notes bar has a **Brawl Online | Emissary** switch: two drafts (`data/patch-notes/draft.json`, `draft-emissary.json`), each with its own past list. The Emissary preview has the tag the launcher puts over them ("Emissary v0.7.2", the next release's version). The Ship drawer's **Release** (and **Push both**) publishes the Emissary draft once the release is the latest (stage `notes`, after `latest`: `ssh … sudo pp-admin changelog publish --emissary v0.7.2`); an empty draft publishes nothing. So they are never out before the release they describe. "Show on staging" puts it on staging too (`--every-start --emissary <next version>`).
- **Launcher.** One popup, one feed: a launcher whose Play uses EmissaryRecomp (Settings > Game) asks for the feed with `emissary=1` and gets both, by date; EmissaryRecomp's have a small "Emissary v0.7.2" tag over them (`changelog_dialog_view.tsx`). Push both is one popup with both. Dolphin players never get them, in the popup or in Settings > Changelog. A recomp release comes without a launcher update, so such a launcher asks at every start (not only after an update) and opens the popup when the newest is new (`changelogSeenAt`); the launcher's build time doesn't hold them back. Nothing opens while the game is running or when Play is pressed: one published while the launcher is open shows at its next start.
- **Discord.** The bot asks with `emissary=1` and posts EmissaryRecomp's to #emissary-updates as soon as they are published (`EMISSARY_UPDATES_CHANNEL_ID`), the launcher's to #updates as before.

## Server

- `changelogs` (migration 0046): `body_md`, `published_at`, `every_start`; 0047 `product` (`launcher` | `emissary`) and `version` (an Emissary one's release). Every changelog stays as the history (`pp-admin changelog list`, Emissary ones marked `[emissary v0.7.2]`).
- `emissary=1` on `GET /v1/changelogs`: EmissaryRecomp's too, with `product` and `version` (`before` doesn't apply to them), and their every-start one on the first page. Without it, and in `/latest`, only the launcher's (older launchers never see them). `pp-admin changelog publish --emissary v0.7.2` publishes one; its every-start one is replaced per product.
- `GET /v1/changelogs?limit=&before=&after=` (public, `max-age=60`): the feed, `{changelogs: [{id, html, markdown, publishedAt, everyStart}], next}`, newest first, rendered by `blog::render`, `limit` 2 by default and at most 5. `before` (RFC 3339, a launcher's build time) leaves out the ones published after it; `next` is the opaque cursor for `after` (published time and id), null on the last page. The first page (no `after`) starts with the every-start one if there is one, whatever `before` says. 400 `bad_cursor` / `bad_before`.
- `GET /v1/changelogs/latest` (public, `max-age=60`): `{changelog: {id, html, markdown, publishedAt, everyStart} | null}`, the every-start one if there is one, else the newest. The launchers before the feed ask this; kept for them.
- `pp-admin user directory`: every account with a code and not banned, a JSON line each (uid, code, name, the Discord username on its profile), for the board's `@` list.
- `pp-admin changelog publish [--every-start] | clear-every-start | list | render` (`server/crates/admin/src/changelog.rs`, `accounts::changelog::publish`). `publish` refuses a picture that is neither sent nor already in the media folder, and anything that isn't a PNG, JPEG, GIF, WebP, AVIF, MP4, WebM or MOV (by its bytes). Audited as `changelog.publish` / `changelog.publish_every_start`.
- Tests: `changelog::tests`, `mentions::tests`, `e2e --test changelogs` (`changelog_mentions`) (`changelogs_feed_pages`: pages, `before`, the every-start one, bad cursors); launcher `main/changelog_version.test.ts`, `lib/changelog/changelog_html.test.ts`.

## The first push

The board publishes with prod's pp-admin, which learns `changelog` from the push that brings this code. So for that push the board publishes after it: when publishing before the push fails because prod's pp-admin doesn't know `changelog` (or the table isn't there yet), it notes the time a minute before the push, pushes, then tries again every 20 s for up to 45 minutes (the server deploy takes about 8) with `pp-admin changelog publish --published-at <that time>`. Every launcher that push builds was built after that time, so it counts the notes as published before it was built. A launcher that updates and starts before they are published finds none and asks again at its next start (`latestChangelog` answering null leaves `changelogPending`). If the 45 minutes pass, the push is done but the board says the notes are not published, with the command to publish them by hand. From the push after it on, publishing goes before the push as above. `--published-at` takes a time at most 2 days back and never ahead.
