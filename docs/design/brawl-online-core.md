# Brawl Online core: one online implementation for Dolphin and EmissaryRecomp (design)

Status: merged into main (439552bb4, 2026-11-25; the last fix left on its branch came in with 4dd5e98c2). **EmissaryRecomp work in this repository is committed to main now**, like any other change; `emissary-recomp` and the other `emissary-*` branches are retired, so don't start new branches for it (Sarah's board, card 810). The recomp's own side goes on EmissaryRecomp's `brawlonline/windows-build`, the branch staging builds. Built on branch `emissary-recomp` from 2026-11-13 (steps, §8). Decisions 2026-11-13 (§7). The user's request (Sarah's board, 2026-11-13): "we need to get rid of the companion app. i know dolphin and the recomp are both c++(?) so maybe it would make sense to have one submodule that both depend on??? it would also require a lot of tests to make sure nothing at all changed when we modularize it out."

## 1. Today

- **Dolphin** does everything around the game in C++: `dolphin/Source/Core/Core/Online/` (18,000 lines: GameBridge, Rooms, Matchmaking, GameSetup, Chat, RoomMessages, Ranked, Spectate, RoomWatch, SpeedCheck, User, ...) and `Rollback/GameplaySession.cpp` (11,700 lines: the session's state machine, setup sync, GekkoNet, replays, desync recovery), on top of Dolphin's emulator (memory, CPU, CoreTiming, video, audio).
- **EmissaryRecomp** (PR #2) has only the rollback engine in the game (GekkoNet, snapshots); everything else is kalomaze's Python companion (`tools/online`, ~1,500 lines, Direct and Unranked 1v1 only) plus our `mmclient` binary, driving the game over a loopback control socket (memory read/write, gates, arm).
- Both are C++ (the recomp's runtime is C++17/20, built with clang; Dolphin C++20 with MSVC/clang/gcc). The plugin (PPOnline) is the same in both: it talks through the PPOM block in game memory.

## 2. The idea

Move the online code out of Dolphin into a library with no Dolphin types, **brawl-online-core**, behind two small interfaces each engine implements. Dolphin keeps its behaviour exactly (it calls the same code through the interfaces); the recomp links the same library in-process, and the companion and the control socket go away.

```
                 brawl-online-core (C++20, no Dolphin, no recomp)
   ┌─────────────────────────────────────────────────────────────────────┐
   │ protocol/   PeerData (wire), RoomMessages, MatchRules, SetFormat,    │  pure
   │             ChatText, ChatCrypto, ReplayFile (.brep), constants       │
   │ net/        Matchmaking (ENet mm client), Ipv6, User, Ranked, Chat,  │  needs Services
   │             Spectate, RecentCodes, OnlineClient, OnlineSession       │
   │ game/       GameBridge (PPOM), GameSetup, Rooms, RoomWatch,          │  needs Services +
   │             SpeedCheck, ReplayRecorder                               │  Engine
   │ session/    the session state machine of GameplaySession: arm, setup │
   │             sync, barriers, GekkoNet events, checksums, desync       │
   │             recovery, quits, game-status.json / join-room.json       │
   │ third_party GekkoNet (Brawl Online's copy), ENet                     │
   └─────────────────────────────────────────────────────────────────────┘
          ▲ Services (host services)            ▲ Engine (the game under it)
          │  log, files, paths, config,         │  read/write guest memory
          │  threads/timers, HTTP, UDP/ENet,    │  save/load a frame's state
          │  on-screen messages                 │  advance one frame (run the game loop)
          │                                     │  loop-top / stage-create / barrier hooks
   ┌──────┴──────────┐                   ┌──────┴────────────────┐
   │ Dolphin         │                   │ EmissaryRecomp runtime │
   │ (RollbackManager│                   │ (brawl_rollback.cpp's  │
   │  CoreTiming,    │                   │  snapshot store, its   │
   │  JIT, VI, DSP)  │                   │  interpreter hooks)    │
   └─────────────────┘                   └────────────────────────┘
```

`Guest` (GameplayRollback.h) already wraps guest memory reads behind one class; most game-facing code goes through it, which is where `Engine` starts.

### 2.1 What stays in Dolphin

Whole-machine rollback (`MachineSession`, `MachineSDCard`: Other Games), replay playback and its Dolphin-only parts (ClipRecorder, keyframes), RollbackManager and every JIT/CoreTiming/VI/audio detail of saving, loading and hiding re-runs, harness hooks. The core never sees them: Dolphin's `Engine` implementation calls them.

### 2.2 What the recomp provides

Its `Engine`: guest memory (`Memory::`), save/load (its snapshot store, now driven by the core's session instead of its own copy of the loop), "run one frame" (its loop hook at `0x800171B4`), the stage-create and loop-top hooks it already has. Its `Services`: SDL/std threads and timers, sockets (it already has portable ones from kalomaze's transport work), curl or WinHTTP for HTTP, its log. Then the runtime reads `User/Online` like Dolphin does: no companion, no control socket, no Python, no `mmclient`.

## 3. Where the code lives

Every protocol change today is one commit in this monorepo (server + Dolphin + plugin + launcher). That has to stay true, so:

- **The core lives in the monorepo** (`core/` beside `dolphin/`, `server/`, `game-code/`); Dolphin builds it from there with no submodule.
- **EmissaryRecomp fetches only `core/`** at a pinned commit of this repo, in its `build.py` as it fetches its other dependencies: `git clone --filter=blob:none --no-checkout`, `git sparse-checkout set core`, checkout of the pin (a few MB, not the 162 MB repository; a git submodule can only take a whole repository). Bumping the pin is the "recomp protocol" update of brawl-recompiled.md §7.4.

(Alternative: the core as its own repo, a submodule of both. Simpler mechanics, but every protocol change becomes two commits in two repos in the right order, which is where Dolphin and the plugin would start drifting.)

## 4. Proving nothing changed

**Machine code, for the moves.** A step that only moves files (and repoints includes) is checked by the instructions themselves: each moved file's object in `brawl_online_core` against the object it had in Dolphin's `core` target, disassembled (`dumpbin /disasm`) and compared function by function (`E:\emissary\scripts\fn_compare.py` for now; anonymous-namespace path hashes and string-constant names are normalised, the latter differing only by the log macros' `__FILE__`). For that the core is compiled exactly as Dolphin's own code: added from `dolphin/Source/CMakeLists.txt` (Dolphin's Source-level definitions) with Dolphin's precompiled header. Steps 1 and 2a: 592 of 592 functions identical.

**The same header names, not a new interface, for Dolphin's helpers.** The moved code keeps including Dolphin's `Common/...` headers (files, timers, ENet, HTTP, UPnP, random, logging, settings). In Dolphin's tree those are Dolphin's headers, so the moves change no instruction; EmissaryRecomp provides headers of the same names with its own implementations (kalomaze's `gekkonet_compat/Common/Logging/Log.h` already does this for GekkoNet). A `Services` interface (§2) would have changed every call site, and so every function, before the recomp needs any of it. `Engine` (guest memory, save/load, the frame hooks) is still a real interface: Dolphin's emulator headers can't be stood in for.

The other checks:

The extraction is a refactor: Dolphin must behave byte for byte as before. Before the first step, a baseline is recorded with today's main; after every step it is recorded again and compared.

## 10. EmissaryRecomp in-process (2026-11-15)

Sarah's goal: the core end to end in EmissaryRecomp, tested and not desyncing (recomp against recomp, then against Dolphin), so the rest is UI, QA and speed.

- **Standalone build (core/standalone/, 00afd805).** Built outside Dolphin's tree from what the recomp fetches with a sparse clone: `core/`, `dolphin/Source/Core/Common` (Dolphin's own Common, compiled as is), `dolphin/Source/Core/Core/Brawlback/include` (GekkoNet, constants), a few Dolphin files the core reuses as they are (FrameProfile, UdpSocket6, ReplayPlayback, GameplayOnlineBackend; their headers are copied into the build's own include root, so Dolphin's real `Core/` headers are never seen) and the Externals they use. Toolchain: the recomp's llvm-mingw clang, C++23. Dolphin's Common has a few MinGW guards (share modes, stat, SEH in SetThreadName, cpuid), each false under MSVC. GekkoNet: the recomp's vendored copy (identical to Dolphin's) when the parent build has the target (`BRAWL_ONLINE_GEKKONET_TARGET`), else its own.
- **Compat headers (core/compat/include).** Same-named stand-ins for the Dolphin `Core/`, `VideoCommon/` and `InputCommon/` headers the core includes (`AudioCommon/`'s went with §10.4), over `BrawlOnline::Host` (guest memory, on-screen messages, local pads, stop, host jobs, `HarnessActive`); no-ops for Dolphin-only parts (Other Games' MachineSession and mods rooms, clips, frame profiles, present stats, GPU FIFO).
- **The recomp side** (EmissaryRecomp, our branch `brawlonline/windows-build` on PR #2): `runtime/include/brawl_online_bridge.h` joins the two halves in plain types (both have a `Memory`); `runtime/brawl_online/` is the core's side (the Engine and Host over the bridge, the hooks), `runtime/src/brawl_online_core.cpp` the runtime's. The loop: at `LOOP_TOP` (0x800171B4) the core says go on, skip (the loop end, then one `VIWaitForRetrace`, as Dolphin's CPU keeps running while its throttle paces), or call (a guest function, then the loop top again); `FRAME_END` (0x80017504) and `LOOP_END` (0x80017508) are interpreter pc hooks; the pad thread's read and update run where updateLow returns (0x8002BA84); the stage hooks at `__ct__7stMelee` and 0x80949BC0. Snapshots: the recomp's SnapshotStore and WriteWatch over the region set the core resolves (merged by physical address), a ring of 8 like RollbackManager's. Time: DetClock (60.75 MHz time base, paced to real time). The harness protocol (JSON lines over TCP, `brawl_online_harness.cpp`) answers what the online tests use, so ppharness drives a recomp as it drives Dolphin (`harness/ppharness/recomp.py`, `PPHARNESS_RECOMP` / `PPHARNESS_RECOMP_NAMES`), and a test can pair one with a Dolphin.
- **MEM1's mirrors.** Leaving the stage select where anyone picks, P+ online's automatic A finds no port that pressed it and Brawl reads a pad status of port -1 (gfPadSystem - 0x40), whose word 0x805BA480 indexes a table at 0x806B91C8 to 0x8348B5C8. Dolphin masks that with its 32 MiB RAM mask (MEM1 0x8148B5C8, a real value that decides a branch); the recomp had no mapping there and crashed. The recomp now maps MEM1 again every 32 MiB of 0x80000000-0x87FFFFFF and 0xC0000000-0xC7FFFFFF (views of the same backing).
- **Pads.** A harness recomp has a controller on port 1 only, as Dolphin's harness instances do (the other ports read error 0xFF), so the game's pad memory is the same on both.

Speed (2026-11-19, after merging kalomaze's experimental-horizon-optimizations, recomp 771c27b): the recomp holds 60 fps in a match against Dolphin, and a rollback costs 6-9 ms on average (about 2 frames deep, max 27 ms) through netsim's bad_wifi. Before, it ran 40-51 fps with rollbacks of 30-75 ms: 45% of its game thread was in `GuestCodePatch::Sync()` (RunPatched syncs after every call of a patched function, and each sync compared every open code-and-data page word by word against its pristine copy); his branch compares each page with its last-synced copy (`g_seen`) and translates P+'s fixed patches ahead of time (code variants). One replay alone: 198.3 s before, 116.5 s now (real time 109 s); Sync() 58.5% of the game thread before, 1.5% now. His other switches: lean memory stays off on PC (its masked window has no MEM1 mirrors, above); MKW_FAST_FLOAT, MKW_EABI_REGS and MKW_LEAN_DIRTY_MARKS=OFF are not for online play (not bit-identical, P+ breaks it, no rollback). Open: once in 50 replays started six at a time, SDL_GPU's Vulkan device was lost at start-up and aurora's thread crashed on it. The Windows build gets no Direct3D 12 driver from SDL_GPU (its shaders are SPIR-V only) and runs Vulkan.

The stop after the start barrier (2026-11-19, branch `emissary-stall`, recomp `brawlonline/stall`). Once in 5 crossplay sets on 11-18 (inst-hzx1), the recomp ran one session frame in 10.3 s right after the start barrier: its GekkoNet sent nothing in that time (its network thread's state messages still came), and Dolphin dropped it after 8 s ("peer timed out"). That frame's "game code" was 9.5 s: the game's thread was inside the game's own pass the whole time, so nothing polled GekkoNet. The cause is the recomp's executable: 240 MB of translated game code, which Windows pages in from disk the first time each part runs. That run was the first set on a new build, run from the harness instance on E: (a USB hard disk shared with other builds), so every code path the game ran for the first time waited for the disk; the match's first frame runs a lot of new code. The later sets found the executable in the file cache, which is why it was 1 in 5 and why the runs with the stall catcher never saw it. Reproduced with a copy of the build nothing had read (robocopy /J), run from E:. The first set's GekkoNet handshake took 9.6 s (normally 0.3-1.1 s), Dolphin waited 13 s at the start barrier, the recomp had 12-23 frames over 300 ms and 2-6 over 1 s (warm: 1 and 0), up to 9,700 pages a second read in at 35-100 disk reads a second, and the loop watch (below) caught the game's thread stuck in the game's code for 1.8 and 2.1 s with no processor time at all on an idle PC; the timeout was not reached in those runs (the disk was less busy than on 11-18), the same symptoms at a smaller scale. The fix (EmissaryRecomp `main.cpp` `PrefetchExecutableImage`): from start-up a background thread brings the whole image into memory (PrefetchVirtualMemory, then one read of every page); a cold copy on E: is in memory 5.4 s after start, long before a match (0.2 s from the SSD). With it, a cold copy on E: under 4 threads of random reads on that disk (57 ms a read) had 1 frame over 300 ms in game 1 and no stall of its own.

The loop watch (core, Dolphin too): the network thread watches lock-free marks the CPU thread leaves (where it is and since when, loop tops, passes, skipped passes and why, its last GekkoNet poll) and, once the session frame has not moved for 1 s (then 3 s, 8 s, every 10 s), logs `gprb: loop watch: session frame N has not moved for ...`: where the CPU thread is, what the loop did, how much processor time the game's thread got against how busy the PC was (`LoopWatch.cpp`: blocked on the disk or a lock = no time on an idle PC; starved = no time on a busy PC; a loop in the game = a whole processor), GekkoNet's last poll and traffic, and `Engine::StallReport()` (Dolphin: nothing, its stall tracer covers it; the recomp: its deterministic clock, whether a guest thread can run, and the game's thread's native stack, resolved with `WiiCompiled.map`). Then `... moves again ... after N s`. In these runs it named all three kinds: the cold executable (recomp, 0 ms, PC idle), Dolphin starved at below-normal priority by other builds (Dolphin, 0 ms, PC 100% busy, 4.9 s), and the recomp waiting for Dolphin (`hostwait`). `PPR_GPRB_TEST_STALL_AT=<session frame>:<ms>` holds that frame's first presented pass (tests); with 10 s on the recomp it gives the 11-18 failure exactly (Dolphin drops it 7 s in), with 2.5 s the set plays on. ### 10.2 Random, sound and time sync in the recomp (2026-11-23)

Sarah, 2026-11-23: "definitely need random, time sync ..." before trying EmissaryRecomp on staging (board card 758). Recomp branch `brawlonline/sync-hooks` (off `brawlonline/windows-build`), this branch `emissary-sync-hooks`.

**Random.** Nothing was missing. Dolphin's srand/srandi hooks (HLE.cpp, `BrawlbackSyncCharSelectRandomSeedHook` at 0x803F8C5C and 0x8003FB4C) act only while Dolphin's own netplay runs (`NetPlay::IsNetPlayRunning()`, which Brawl Online never starts), so they do nothing in our sessions. What makes random the same on both machines is in the core and the plugin, for both engines: the session seeds g_mtRand, the other mtRand and the C library's rand for every match from the host's session seed (`MatchSeeds`, at the scene change and again at the stage's construction, the stage hook the recomp has), and the sync block at the start barrier carries them; a player on RANDOM has the character drawn on their own machine at lock-in (g_mtRand) and sent with the lock-in; game 1's random stage is the host's draw from the server's list (`DrawRandomStage`); the stage select's RANDOM is drawn by P+ on the picker's machine and sent as the pick; a substage P+ picks at random is the agreed one (`PinSubstage`, from the session seed). Test: `test_direct_set_on_random` (new): both players on RANDOM for a three-game Direct set, game 1's stage by START, games 2 and 3 by the loser's A on the stage select's RANDOM; both machines must set up the same match every game (characters, costumes, stage, setup hash) and keep the same confirmed checksums.

**Sound.** Dolphin's session has five sound hooks (HLE_Misc.cpp): the three `bl detail_Alloc{Seq,Strm,Wave}Sound` in `SoundArchivePlayer::detail_SetupSound` (0x801C9AAC, 0x801C9B54, 0x801C9BFC), its success path (0x801C9C70) and `BasicSound::Stop` (0x801BC684). They let the core's sound bookkeeping (`Gprb::Session::OnSoundAlloc`, `OnSoundAttached`, `OnSoundStop`) keep a sound that a frame's earlier run started playing when a rollback runs the frame again: the re-run's start of the same sound is attached to the one still playing instead of allocating and starting a second one, a sound the corrected run no longer starts is stopped at the frame's end, and a "stop the sounds of this owner" in a re-run does not cut off sounds the re-run has not reached yet. The sound archive player's pools are outside the snapshots, so without them every rollback started each of its frames' sounds again: doubled sounds, pool objects used up, orphans nobody can stop, and allocation results (a sound or "no channel") that could differ from the frame's first run (on the recomp nothing called the bookkeeping before: its counters, below, stayed at 0). The recomp now runs those two functions in its interpreter (`GuestCodePatch::InterpretForHooks`, as a mod's patched function runs) and its interpreter calls the same core functions at the same pcs (`BrawlOnlineCore::SoundHook`): Reattach goes on at 0x801C9C70 with r24 = the sound, NoChannel returns null from the allocation, a declined Stop returns to its caller. They run a few times a frame at most. Dolphin's mtRand trace hook (0x8003FAC4, `GprbRngTraceHook`: the desync log's list of each recent frame's RNG calls) stays Dolphin's: mtRand::generate is a leaf inlined into many callers, which would all go to the interpreter.

**Time sync and pacing.** The core's Engine time calls were no-ops in the recomp; they now drive its deterministic clock's pacing (det_clock.cpp: the scheduler's idle waits until real time reaches the next guest event) as Dolphin's CoreTiming throttle does them: `SetRollbackSpeedAdjustment` (the timeline runs at that factor of real time, continuing from the current instant's due time), `AdvanceThrottle` (the schedule moves earlier: a catch-up frame), `BeginRollbackBurst` (the presented frame after a re-run is due where the schedule was when the rollback began), `SetRollbackLoadWait` (no pacing while the loop top waits for loads, paced from then after), `ScheduledHostTime` (the real time the current instant is due: the session's local pad reads on the schedule), `TakeMaxBehindSchedule`, `SetPresentPacing` + `SetPacedSleepLead` (the pacing wait before a frame ends early by the coming rollback's cost, so the rollback runs in it), `ResetThrottleToNow`. Lateness and the lead count only at the next VI retrace, the frame's own pacing point: the recomp's clock stands still while guest code runs, so an event due in the middle of a frame (audio DMA, an alarm) is always found behind by the frame's own work, and counting those made 95% of the recomp's frames "late" (the core takes this PC for one that cannot keep full speed: `behind`, the follow logic, the quality abort's cause, speed reports). The audio waits for re-runs (`SetRollbackAudioWaits`, `AddRollbackAudioPause`) stay no-ops: the recomp's audio follows the deterministic clock. Found with the new tests: the recomp's deterministic clock put a retrace every 16,666 µs (60.00 Hz, its wall-clock default), while a Wii, Dolphin and the core (`FRAME_US`, the engine's 1,013,513 ticks per field) count NTSC fields at 1001/60000 s (59.94 Hz), so against Dolphin the recomp's frames came 0.1% early; time sync held that with Dolphin running ~0.08% fast for the whole match and a steady third of a frame between them (frames ahead -0.25 on Dolphin, +0.44 on the recomp, where Dolphin against Dolphin read 0.00-0.04). With the deterministic clock the recomp's field is now 1,013,513 ticks (vi.cpp `DetIntervalTicks`; PAL stays 50 Hz, and the standalone game's wall-clock pacing with its V-Sync display lock is unchanged), and `VIGetCurrentLine` counts lines against that field rather than the display lock's (which differs from one PC to the next). Test hook `BRAWL_TEST_CLOCK_SKEW=<factor>` (recomp; Dolphin: Core.EmulationSpeed): the match runs that much faster than real time before time sync's factor.

**Logs for a drift report.** Both engines log the session's 10-second windows (`gprb net: frames A-B: ...`: frames ahead avg/min/max, time sync's speed range, catch-up frames, waits for the other player, late frames, rollbacks and their cost, ping) and the loop watch. The recomp adds one line per match, `recomp pacing: emulated X s in Y s real (Z%; re-runs R s more), waited W s for the schedule, speed [min, max], schedule advances N, re-anchored N times (over 100 ms behind), rollback bursts N, waits a coming rollback ended early N`: a clock that runs fast or slow against real time shows in Z, a PC that cannot keep up in the re-anchors.

### 10.4 The audio clock waits for re-runs, and fast playbacks are muted, in the recomp (2026-11-24)

Two of Dolphin's rollback audio fixes were missing from EmissaryRecomp (found on card 762; Sarah: "i'd launch a task to fix the audio, for both those missing features"). Branches: this one's `emissary-audio`, EmissaryRecomp `brawlonline/audio`.

**The audio clock waits for re-runs.** Gameplay-only rollback leaves the sound system out of the snapshots, so a sound plays on through a rollback. Dolphin's audio clock waits for the re-runs (CoreTiming `SetRollbackAudioWaits`, SystemTimers' `AudioDMACallback`): the session adds a field per re-run pass to a pause, and the audio DMA holds that long (no DMA, no AI interrupt, no AX frame, no voice moves), and holds too while the loop top waits for loads. The music and sounds then advance only with the frames that are shown. In the recomp those Engine calls were no-ops, and its AI DMA delivered a block every 182,250 ticks of the deterministic clock, which re-runs move on unpaced. So every re-run's blocks went to the output at once, the output queue (120 ms) filled, and it dropped the blocks after: the sound skipped ahead at every rollback and played ~110 ms late. Now `SetRollbackAudioWaits` / `AddRollbackAudioPause` / `SetRollbackLoadWait` reach the recomp's AI DMA (`hle_stubs.h` `Audio_HLE_SetRollbackWaits`, `audio.cpp` `AudioTickDeterministic`). A block whose time comes during the pause or a load wait is held: no output, no DMA callback, nothing of the guest runs for it. The pause can go below 0 by a block (3 ms against a 16.7 ms field), so the blocks held add up to the pauses. `PPR_GPRB_RESIM_AUDIO=advance` (the core's switch) turns the waits off. In the recomp that means the old behaviour, with the re-runs' blocks played; Dolphin's "advance" drops them instead.

**Fast playbacks muted.** Dolphin silences its sound stream while a playback runs fast: a spectator's or room watcher's catch-up to live, a seek's fast-forward during it, any forward run of a live playback (bug reports #103, #309). The core's `PlaybackMute` called Dolphin's AudioCommon, which were empty stand-ins in the recomp's build. It is now `Engine::SetPlaybackMuted` (`BRAWL_ONLINE_ENGINE_PLAYBACK_MUTE`). Dolphin's engine does what the core did (stream volume 0, back from the user's settings); the core no longer includes AudioCommon, and its compat stand-ins are gone. The recomp drops its output while muted: the AI blocks still run their DMA callback, but their samples are not queued, since a muted queue would still fill at the playback's speed and play late after. The recomp logs `recomp audio: muted (a playback running fast)` and `recomp audio: unmuted, X s of sound dropped while muted`.

**Measured.** The recomp logs one line per match next to `recomp pacing`: `recomp audio: played N blocks (X s) for Y s shown (Z%), held N for re-runs (X s; re-runs R s), N in load waits, N played during re-runs, N muted; output queue avg A ms, max M ms, D of B blocks dropped (full)`. ### 10.5 Input suggestions in the recomp (2026-11-26)

Sarah's board: "has subframe rollback been ported into the recomp?" It had not: since the 11-23 merge the recomp's core had a stand-in that turned input suggestions (`docs/gameplay-rollback-status.md`, GitHub issue #35, Arte's "subframe rollback") off, so a recomp player sent none, used none and predicted every player with their last input. **The core.** Dolphin's `Core/Rollback/InputSuggest.cpp` is the core's as it is (core/standalone reuses it, the compat stand-in is gone). Its two Dolphin-only parts, the Wii U adapter's report hook and the sampler thread's device update and pad read (ControllerInterface, `Pad::GetStatus`, the input gate), moved behind `Core/Rollback/InputSuggestSource.h`: Dolphin's `InputSuggestSource.cpp` keeps them as they were; core/standalone's (`core/compat/src/InputSuggestSource.cpp`) has neither. An engine that samples its own controllers asks `Suggest::SampleChannel()` (the port to look at, or -1 when no look would be used) and hands each look to `Suggest::Sample(chan, pad, start, end)`, which counts it and sends it as a sample of Dolphin's thread is (the same rules, timing, stats). SFML's network target is public on `brawl_online_core_standalone` (InputSuggest.h names its addresses).

**The reads the game gets.** A suggestion is tagged with the frame whose read will first see the change, from the instant the newest local input's read stands for. The recomp's reads had no instants in the core (its passes all said "never"), so the recomp now hands each latched read to the core (`Gprb::EngineHostPadRead`, FrameInput::Latch at every retrace: all four ports). **The looks.** The recomp's controllers belong to its game thread (aurora's pad state, its bindings, Dolphin's controls), and that thread spends most of a field waiting for the next one (DetClock's pacing: 20.7 of 30.6 s in a test game). So the looks are made there: DetClock's waits ask a wait hook first, and while it wants samples sleep in 1 ms slices (a high-resolution timer, no spin) and ask it before each, the last 1.5 ms as the old precise sleep. The hook (`BrawlOnlineCore::SampleForSuggestions`) runs `SDL_UpdateJoysticks` (SDL reads its pads only at the frame's event pump otherwise) and the runtime's whole PADRead path read-only: aurora's new `PADPeek` (PADRead's statuses without touching its held-input suppression, the LEDs or the next read's capture), the Wii Remote hiding, the triggers bound to buttons, the bindings (`InputBindings::Apply(..., peek)`: the bindings' active flags stay), Dolphin's controls on Dolphin's input channel for suggestions (`DolphinPads::UpdateInput/GetStatus(..., suggestions)`, so a mouse's motion stays the game's reads'), the harness's pads without counting a poll (`CoreHarnessPeekPads`); none while a test script drives the pads. A look costs 17-21 us on average.

**The harness.** The recomp's harness has `pad_script_timing` (scripts that step with the host clock from a random point between two reads, as Dolphin's), and `test_input_suggestions.py` has `test_suggestions_crossplay[vs_dolphin|vs_recomp]`.
